# HD-1910 · 策略导出 → 部署链（端到端 + 已知坑）

_日期：2026-11-09。粒度对齐 `microduck-泰山派部署-feetech_hls烤板步骤-2026-11-09.md`。_
_对象：HD-1910 = Feetech HLS 线、B 代 robotd（`DuckBuddy-main`）、obs 61 / act 14 / 50 Hz。_

## 0. 链路总览

```
训练产物 (wandb run / model_<N>.pt)
   │  uv run scripts/export.py <TASK> --wandb-run-path <ent/proj/run> --checkpoint <N>
   ▼
policy.onnx  （normalizer 已烤进图）
   │  uv run publish --onnx policy.onnx --repo <user>/microduck-<name> --kind perpetual --slot walk [--dry-run]
   ▼
HuggingFace Hub repo（policy.onnx + manifest.json + README.md）
   │  （机器人侧）sudo robotctl policy load walk <repo>
   ▼
robotd 加载策略，50 Hz 跑
```

导出封装：`scripts/export.py` 是 `mjlab_microduck.export.main` 的薄壳（`export.py:8`）。
发布：`src/mjlab_microduck/publish/cli.py`（`uv run publish`）。
清单校验：`src/mjlab_microduck/publish/manifest.py`。

## 1. 步骤（带命令）

### 1.1 导出 ONNX（必须走 checkpoint 路径，保证 normalizer 入图）
```bash
uv run scripts/export.py <TASK_ID> \
    --wandb-run-path <entity>/<project>/<run_id> \
    --checkpoint 3000
```
- ✅ 只有这条路径把**观测归一化器烤进 onnx**（`cli.py:3` 注释："exports with the normalizer baked in — the only safe path from a checkpoint"）。
- ⚠️ 手搓 / 只导 raw onnx → 图里没有 normalizer，`publish` 的 smoke 能过，但机器人喂的是**原始观测** → 动作全错，症状像「策略不会走路」。

### 1.2 发布到 Hub
```bash
uv run publish --onnx policy.onnx \
    --repo <user>/microduck-<name> \
    --kind perpetual --slot walk \
    --dry-run          # 先写 ./publish-<name>/ 本地核对，再去掉 --dry-run 真传
```
- 发布前 `publish` 会做：`check_onnx`（obs=61 / act=14 宽度门）、`smoke_run_onnx`（50 步喂零/抖动观测，拒绝 NaN 与常数输出）。
- 一个 repo **只能有一个 .onnx**；覆盖需 `--force`。
- 安装命令由清单生成：`sudo robotctl policy load walk <repo>`（`manifest.py:324`）。

### 1.3 机器人加载
```bash
sudo robotctl policy load walk <repo>
```
- 这是 B 代 robotd（DuckBuddy-main）的 `robotctl`。**不是** kissqy/A 代那套（`deploy_import_checklist.md` B1：两代 schema 不通用，HD-1910 只能用 B 代）。

## 2. 已知坑（逐条带源码位置）

| # | 坑 | 源码位置 / 证据 | 后果 |
|---|---|---|---|
| P1 | **normalizer 必须烤进图** | `cli.py:3`（仅 checkpoint 路径烤入） | 手导 raw onnx → 机器人吃原始观测 → 动作错 |
| P2 | **ONNX 外部权重陷阱** | `manifest.py:237` `onnx.load(..., load_external_data=False)` | split / EXTERNAL 权重 onnx 过形状检查、上传 **3 KB 空权重图** → `robotctl` 加载无权重网络 → 动作垃圾。发布前必须确认权重在图内、onnx 体积合理 |
| P3 | **obs/act 门 = 61/14** | `manifest.py:269-275`（OBS_LEN=61, ACTION_LEN=14） | 51-D 旧家族被拒；HD-1910 策略必须是 61-D |
| P4 | **manifest `robot.servos` 硬编码 "xl330"** | `manifest.py:28` `ROBOT = {... "servos": "xl330" ...}`；`validate_manifest` 只校验 `robot.model=="microduck"`（`:204`） | 发布的策略**声明 xl330 却装在 HLS 机器人上**——daemon 忽略 servos 字段，能加载，但元数据是错的（这就是旧记忆「manifest 字段不生效」的精确落点） |
| P5 | **`rehearse_deploy.py` 写死 BAM XL330 / kp_fw=200** | `rehearse_deploy.py:144`（"BAM M6 on xl330 ... kp_fw=200"）、`:627`（`args.kp_fw = 200.0`） | 这是 XL330 执行器模型 rehearsal，**不能用于 HD-1910**。改用 upstream `scripts/infer_policy.py` 或本仓台架 harness |
| P6 | **`[policy] gain` 是 XL330 口径，不是寄存器 P** | `feetech.rs:115` `KP_REFERENCE=200`；`out/robotd_hd1910_mode0.toml:51-52`（显式 `gain=200`） | 写 `gain=8` → `reg50=clamp(round(0.32),1,254)=1` → 每颗 P=1 → 瘫软 |
| P7 | **真实 P 杠杆是 `position_kp`（默认 8，部署 16），D 是 `position_kd`（默认 8，非 0）** | `feetech.rs:236`（reg50 公式）、`:399`（写 reg51）、toml `position_kp=16` | D 写 0 会失去阻尼；低位 position_kp 让「瘫软/回站姿」撞同一个值 |
| P8 | **lowpass 默认 0.5/0.7 必须改 1.0** | `toml:56-57`（`head_lowpass=1.0`/`legs_lowpass=1.0`）；导入清单 B10 | 训练零低通；留默认等于给策略加 τ≈17 ms 一阶滤波 |
| P9 | **`[bus] fast_sync_read` 不存在** | 导入清单 B10（DuckBuddy 树出现 0 次） | 写进 toml = `deny_unknown_fields` 拒绝整份文件，robotd 起不来 |
| P10 | **EEPROM 开机硬校验：reg6=1（500k）/ reg33=0 / limits 0-4095** | `feetech.rs:386`；toml 头部注释 `reg6=1`、`reg33=0` | 不满足 → `IoError::Bus` 拒绝启动（checked, not corrected）。出厂 reg6=0(1M)/reg33=4 → 两颗必改 |
| P11 | **保护开关 reg19 必须=13**（逐颗 EEPROM 写） | 导入清单 B11 | 出厂仅 4（过热）；过压/过流/过载/磁编全关 → 撞住不卸力，只有过流 3.25 A 兜底 |
| P12 | **`[bus] joint_ids` 15 条，Feetech 必需** | 导入清单 B12（`robotd/src/main.rs:5495` 有测试） | 空/重复/缺失 → 总线拒绝打开 |
| P13 | **`control_hz` 50、act 14 = 14 舵机** | `manifest.py:28`（`control_hz: 50`）、`:27`（`ACTION_LEN=14`） | 与 robotd 节拍一致；14 维 = 15 颗里的 14 个可控关节 |

## 3. 上板自检（来自 `deploy_import_checklist.md` B2/B8）

1. `robotctl health`：bus 绿；loop **50 Hz 0 missed**。
2. 回读 reg50：腿应读到 `round(gain × position_kp / 200)` = **16**（部署档）；读到 1 ⇒ P6 被人改成 `gain=8`；读到 8 ⇒ `position_kp` 还是默认 8；读到 4 ⇒ 刚跌倒过 `gain_limp` 还在 RAM。
3. IMU 读到且俯仰偏差运行时校掉（BNO08x，`imu_mount_quat` 与 build-tutorial 逐位一致）。
4. 契约：obs 61 / act 14 / 50 Hz 与训练一致。
5. 增益标度家族比例保住（`gain_limp=50→2`、`standing=0.8→6`、`limp_fall_pose=160→6`，全过 `kp_for_gain`）。

## 4. 与上游的关键差异（务必分清）

- 上游 robotd 目标是 **XL330**；我们 HD-1910 是 **Feetech HLS**。发布链的 `manifest.py` 仍把 `servos` 写成 `xl330`（P4），但 B 代 daemon 只看 `model=="microduck"`，故能交叉加载——**元数据错、运行对**。
- 历史 `deploy61` 路径（归一化分母 10 维 = 1.113e-05，差 1157× → 5.7° 头命令变 −35.7 rad）**已弃用**；改用 `p8head_2999`（run `2026-11-03_08-33-18_p8head_030_4096x3000/model_2999.pt` → `p8head_2999.onnx`）。
  - ✅ **编号已实测核对(2026-11-09)**：`p8head_2999` ONNX obs61/act14、`parity_ok=true` 且 `control_detects_missing_normalizer`(7166 处坏) ⇒ 归一化正确烤进图；**default plant + kp8 plant(额定等效, vin 6.5–8.2V) 双 plant 实测均 `terminated_frac=0`、upright≈0.997、no_fall/stays_upright/translates_forward/feet_clear_8mm/steps_alternate 全 PASS**（kp8 plant = `eval_velocity_kp8_p8head_model2999.json`）⇒ **真·走路级、跨 plant 稳走，部署首选**。唯一未过门是 `tracks_half_command`/`error_vel_xy_le_0.25`（实测 vx≈0.167 vs 命令 0.4，速度只达成一半，是训练命令上限设置问题，非不稳）。
  - ⚠️ **`resume_5999` 不要用作部署候选**：run `2026-10-27_08-37-16_hd1910_resume_4096_to6000_1027/model_5999.pt` → `hd1910_resume_4096_to6000_1027_it5999.onnx`，ONNX 归一化确也正确(parity_ok，7167 处坏)，但**走路很差**——自家 plant(default & kp8) eval `terminated_frac≈0.83`、no_fall/stays_upright/translates_forward 全 FAIL；仅 p2_yaw 那次用错配 plant(m5.json/kp_fw=32)才 PASS，不具部署参考性。"good" 只指归一化正确，不指走路。
- 台架（PC + URT-2 + 单舵机）跑 robotd / 工具链 **¥0**；导出/发布链在台式机即可完成，无需上板。
