# MicroDuck 安卓 App 开发规范

> 本规范借鉴 `hbweb-portal/DEVELOPMENT-GUIDELINES.md` 的结构与写法，整理自本项目开发过程中反复强调并长期执行的工作准则，是本项目所有开发活动的强制遵循。
> 每条规范均标注了执行要求与本项目的实际依据（含已踩过的坑），新增代码、修改代码、技术选型时必须对照执行。

---

## 一、总则：遇到问题，先查资料，再动手

**这是本项目最高优先级的规矩，优先于一切技术动作。**

### 1.1 触发场景

凡是遇到下列情况，第一反应是去网上找现成方案/官方文档/别人的实现，**不是自己推导**：

- 报错、异常、构建失败、类型错误；
- 算法实现、第三方库用法、API 用法（含 Android 平台 API、MDC 组件行为）；
- 坐标系/单位/轴向约定、兼容性处理、版本行为变更；
- 别人踩过的坑、已知的静默问题；
- 选型、建库、盘点类任务（先找现成的语义索引/官方目录/标注，再造分析工具）；
- 判断「某个能力/数据集有没有」时，要和数据源本身一起查。

### 1.2 查找顺序

1. **官方文档 / 官方示例**（本地包内 `Samples~`、官方站点文档也要翻）；
2. **一手仓库源码与文档**（用 `api.github.com` / `codeload.github.com` / `raw.githubusercontent.com` 拿真实数据核实，**不要信搜索引擎给的仓库名**——聚合/镜像站会把仓库名拼错或凭空生成）；
3. **社区实现对照**（多个来源交叉验证）。

### 1.3 查不到时的处理

确实找不到现成方案、只能自己推导时，**必须明确说明「这是推的，未找到现成方案」**，并在实现后做充分验证，不得把推导结果包装成有依据的方案。

### 1.4 资料的价值边界（重要）

找资料**必要但不充分**。静默 bug 大多出在「自己那一行代码的语义差」上，外部资料不可能覆盖。

- 资料的价值是提供「**应该是什么**」，让「实际是什么」可比较；
- **验证不能只问「结果对不对」，要问「这个量动没动、量级是多少」**；
- 引入每个奖励项/物理量/派生字段前，先单独测其分布（min/p50/max），确认随状态变化、量级符合预期，再往主流程接；
- 自检必须有**负对照**：故意改坏 → 检查必须变红。只见过绿色的断言不是证据；
- 涉及坐标系/单位/轴的量，必须用**两条独立算法**算同一个量再比对。

> 项目实例：SHA-256 十六进制编码一度把**正确的**字符表误读成错表，还用同一串当判据得到 `OK=True` 假绿；后用 JDK17 `HexFormat` 互算 + 逐字符核验才证伪。教训：判据必须**独立于被测值**，用被测值本身当判据会得到恒真的假绿。

## 二、资料依据规范：每一项都要有支撑

### 2.1 强制要求

**项目里做的每一项技术决策、每一处代码写法、每一个界面元素/布局/结构，都必须有资料支撑，不能乱写、不能臆造。**

- 引入新技术、新依赖、新组件、新写法、新界面结构前，先查证其来源（官方文档、规范条款、成熟项目实现）；
- 落地时在代码注释或提交说明中**标注依据来源**（如「依据 M3 navigation bar guidelines」「借鉴 KaringX/clashmi 的 X 实现」「依据 Google Android 平台文档 Y」）；
- 无依据的写法视为不合规，评审时不予通过。

### 2.2 依据来源优先级

1. **唯一官方原厂**：本项目唯一「官方/原厂」是 **Pollen Robotics 原厂**（`pollen-robotics/microduck` 公开仓库 main 分支及原厂设计文档）。fanhao fork、B 代、Reachy Mini、Google/Android、JetBrains、QGC、NIST 等一律写「机构名 + 平台文档/规范」，**禁称官方**；
2. **官方文档与官方示例**（Android 平台文档、MDC 组件文档、AOSP 源码）；
3. **成熟开源项目的同类实现**（先确认同类度，再借鉴其模式）。

### 2.3 术语约定（强制）

术语必须准确，**编造引用零容忍**：

- 写文献/章节/条文前**一手核验原文**，查不到就删或降级，**禁写「§A/§B.1」这类想当然的编号**；
- 「GitHub 官方 API」→ 写「GitHub REST API（`api.github.com`）」；
- 引用开源项目须写**仓库全称 + 具体文件/方法**，不写模糊的「某项目某做法」。

> 项目实例：曾把「Falcon 控制站排版文献」张冠李戴地挂到等宽数字（tnum）依据上，复核 falcon.so 原文**没有**该句（该文献讲的是状态停滞告警，不是数字排版）⇒ 删除错误引文，只留可逐字核验的 AndroidX `FontSetting.tabularNum()` 源码。

### 2.4 同类度判断

借鉴开源项目前先判断**同类度**：

- 参考的是**同场景实现**（如机器人遥控 App、更新组件、BLE 栈），才直接借鉴其模式；
- 参考的是**不同场景**的实现，只取其**通用技术模式**（请求层、工具函数、容错、串行化等）；
- 无场景的能力不引入，**不因为「别人有」就加**。

## 三、功能边界规范：没有的功能不要乱加

### 3.1 核心边界

**只做两类事，除此之外不新增用户可见功能：**

1. **还原既定功能**——本 App 的用户可见交互、页面、能力以原厂设计（`docs/design/mobile-app.md` 等）与已确认的功能清单为准；
2. **纯内部技术改进**——网络层、工具函数、构建优化、容错、性能、安全加固、代码质量等，用户无感知但提升工程质量。

### 3.2 内部技术改进的识别与执行

**「有没有可进行内部技术改进的地方」是每次开发、每次审查时都要主动思考的问题。** 内部技术改进指**用户无感知、但提升工程质量**的改动，允许且鼓励持续做。识别与执行准则：

**可进行内部技术改进的方向（按优先级）：**

1. **健壮性**：BLE GATT 操作串行化、回调线程纪律、空值/异常兜底、资源泄漏清理；
2. **安全**：下载校验（SHA-256）、签名证书比对、网络明文限制、敏感信息（密钥/密码）不入库；
3. **性能**：构建优化、包体、渲染优化、条件请求（ETag）；
4. **可维护性**：重复代码抽取、单一真源（如 `core/Hex.kt`）、配置驱动替代硬编码、类型完备；
5. **规范合规**：代码规范工具链（lint）、界面结构对齐设计规范；
6. **工程效率**：构建配置优化、依赖治理、脚本工具化（发布脚本、门禁脚本）。

**识别方法：**

- **主动审计**：定期扫描现有代码，找重复、遗漏、反模式、潜在风险点；
- **借鉴时对照**：研究其他项目时，顺带对照本项目找可改进处；
- **验证时发现**：lint / 构建 / 行为验证暴露的问题；
- **回归检查**：修复一个问题时，顺带排查同类问题是否存在。

**边界（重要）：**

- 内部技术改进**不得改变用户可见的行为与页面渲染效果**（除合规必需项外）；
- **不得改变接口契约**，不得借「内部改进」之名新增用户可见功能；
- 改进要有依据（资料/规范/最佳实践），不得为改而改、引入无依据的「自创优化」；
- 改进后必须全量验证，确认渲染结构与功能无回归。

> 项目实例：BLE GATT 操作串行化（`SerialGattLink` 下沉到 core）、入站通知独立线程、SHA-256 校验、固定签名证书，均为内部技术改进，用户无感知但工程质量提升。

### 3.3 判断准则

判断「有没有这个功能/场景」时：

- **看原厂设计与接口契约，不能只看当前 App 是否已接真实请求**；
- 新增任何用户可见功能前，先问：**原厂/既定清单有没有？** 没有的，不做；
- 拿不准时，以原厂设计为准，不擅自发挥。

### 3.4 唯一例外：合规必需项

以 Android 平台强制规范（如 targetSdk 行为变更、前台服务类型、网络安全配置）为依据的合规补齐，属于**合规必需而非业务功能**，允许在原厂没有明确提及的情况下补齐。判定标准：**依据是平台强制规范，目的是合规，不是新增业务体验**。

## 四、依赖与工具规范

### 4.1 构建与依赖管理统一 Gradle

- **项目统一使用 Gradle**（`gradlew`），所有构建、依赖管理一律走 Gradle，不得混用其他构建工具；
- 依赖版本在 `build.gradle.kts` 中显式声明并锁定在稳定版本线；
- 构建前**必须显式设置 `JAVA_HOME`**（本项目用 `E:/软件工具/OpenJdk17`，JDK17，major 61）；
- 网络依赖下载受代理/镜像影响时，优先配置官方镜像（如阿里云 Google 镜像置顶）跑通，不盲改依赖版本。

### 4.2 依赖选型原则

- **依赖用新的且兼容的**：优先选用**新版本且与项目技术栈兼容**的依赖；
  - 版本更新在**不破坏兼容性**的前提下尽量用新版本，锁定在稳定版本线，不固守过时版本；
  - 选型时**先查证兼容性**：新版本的 peer 依赖、API 变更、与 Kotlin/AGP/Gradle/JDK 技术栈的匹配度，确认兼容后再采用；
  - 「新」以**稳定版**为准，不盲目追最新预览版/实验版；「兼容」是硬前提；
  - 升级依赖必须回归验证（编译 / lint / 自检 / 真机门禁），确认无破坏性变更后再落地；
- 依赖搭配先调研、再定稿，**按最优方案执行**；
- **无场景的依赖不引入**；能升则升，锁定在稳定版本线。

### 4.3 组件选型的边界

- 引入新组件前先查证其在本项目 MDC 版本下**是否可用**（如 M3 Expressive 的 button group 在 MDC **1.12.0 baseline** 中不存在，**不能**直接用，只能借鉴其思路用现有组件实现，并如实标注）；
- 不为了「新」而引入与当前技术栈不兼容的组件。

### 4.4 第三方资源与产物处理

- 第三方闭源资源、生成的构建产物（`build/` 下的 APK、临时探针、负对照包）**不入库**；
- 密钥、密码、keystore 等敏感信息**不入库**，只放在项目外的本机配置或已被忽略的 `local.properties`。

## 五、代码规范

### 5.1 工具链（强制）

项目代码必须符合开发规范，落地完整工具链并全量执行：

- **编译**：`./gradlew :app:assembleDebug`，构建必须成功；
- **lint**：`./gradlew :app:lintDebug`，0 errors；
- **自检**：`tools/selftest.sh`，core 纯 JVM 自检全绿；
- **真机门禁**：`tools/device_ui_check.py`，59 条断言全过。

**验证标准：以上全部通过（全绿）才算代码合规。** 既有文件的历史不合规也要逐步修平，不留死角。

### 5.2 代码写法

- 写法须符合相关要求、有资料支撑，不写无依据的「自创语法」；
- **视觉 token 必须具名**（如 `CORNER_LARGE_DP`、`STROKE_HAIRLINE_DP`、`TABULAR_FIGURES`），不把字面量散落在调用点，改一处即可全局生效；
- **单一真源**：同一语义只维护一份实现（如 hex 编码收敛到 `core/Hex.kt`，两处消费链 import 同一函数）；
- 安全相关写法遵循权威依据（如下载校验 SHA-256、安装用 `PackageInstaller.Session`、`PendingIntent` 在 targetSdk≥35 须 `FLAG_MUTABLE`）。

### 5.3 界面结构规范

**界面每一个元素、布局、结构、设计都应该有资料支撑，而不是自己瞎想的。**

- 界面元素/布局/结构落地前，先查官方规范或成熟实现，标注依据；
- 界面改动**不得改动真机门禁的断言文本**（59 条断言子串是硬约束），结构优化通过调整布局实现，而非改断言迁就；
- 界面改动后必须过真机门禁，确认渲染结构无回归。

## 六、质量与验证规范

### 6.1 有问题就修复

- 发现的问题（报错、缺陷、不规范、潜在风险）**必须修复，不得搁置或绕过**；
- 发现问题先查资料定位根因，再修复，不盲目试错；
- 修复后必须回归验证，确认问题真正解决。

### 6.2 验证要求

- **每完成一项改动，必须验证**：编译 / lint / 自检 / 真机门禁全绿；
- 关键逻辑（如串行化、校验规则、状态机）要有**行为断言 + 负对照**验证，不能只看「没报错」；
- **验证要问「量动没动、量级对不对」，而不是「结果看起来对不对」**；
- 判据必须**独立于被测值**——用被测值本身当判据会得到恒真的假绿；
- 交付前做全量验证，不留已知问题。

### 6.3 不遗留（状态真实）

- **`UNVERIFIED` 不等于 `PASS`**，`COLLECTED` 不等于 `PASS`；
- 不把已知问题、待办、未验证项当作完成；
- **任务状态必须与实际进度一致，完成即更新**，不悬挂、不虚报；
- 整机落地前 `ship_verdict` 恒为 `NOT_SHIPPABLE`，不得虚报可发布。

### 6.4 提交规范

- **只提交安卓工作流**：硬件、采购 xlsx、CAD、临时产物（`.tmp/.ref/.bak/_*.png/tools/_*.py`、构建产物、探针）一律不入库；
- 提交前核对暂存区，**不提交密钥/密码/keystore**；
- 提交后必须 `git rev-parse HEAD` + `git show --stat HEAD` **核实提交内容真的包含预期文件**——`git commit` 输出「nothing added to commit」但提交其实已创建的情况已发生，不能只看输出就以为没提交；
- push 偶发 502 时记录 `$?` 重试，不静默吞掉。

## 七、执行准则

### 7.1 按最优方案执行

- 遇到多方案选择时，**调研后按最优方案执行**，不停留在「能用就行」；
- 「最优」的判定：有资料/规范依据、符合项目边界、工程质量高、维护性好；
- 用户未明确指定方案时，自主调研并选择最优方案落地，同时说明依据。

### 7.2 多找几轮开源项目参考，深度挖掘，取长补短

**持续多轮地找开源项目做参考，深度挖掘，取长补短**，这是本项目获取技术方案的重要途径。

**执行要求：**

- **多轮、持续**：不止找一轮，随项目推进分多轮找参考，每轮聚焦不同方向，逐步拓宽借鉴面；
- **深度挖掘**：对参考项目做源码级深度挖掘，不停留在表面功能，逐文件、逐模块地看其架构组织、网络层、组件封装、工具函数、容错处理、构建配置、规范实践；
- **取长补短**：只取其**长处、可借鉴处**，对照本项目短板补强，不照搬不适合的部分；
- **先查证再落地**：每项借鉴先确认来源真实性（用官方 API 核实仓库），判断同类度，有场景才引入，无场景不引入；
- **落地标注依据**：借鉴项在代码注释中标注来源（借鉴哪个项目、哪个实现），保证可追溯。

> 项目实例：更新功能分多轮深度挖掘 KaringX/clashmi（清单/SHA256/防重入）、ImranR98/Obtainium（GitHub Releases/APK 筛选）、Tobi823/ffupdater（证书校验/安装）、javiersantos/AppUpdater（versionCode），每项均先查证、判断同类度，只取通用技术模式，无场景的能力不引入。

### 7.3 先调研，再落地

- 任何动手前先调研清楚（资料、规范、同类实现），再实施；
- 调研结论要记录（落 `docs/active/`），落地要标注依据，保证可追溯。

### 7.4 无场景不引入

- 借鉴、选型、引入能力时，先确认本项目**有没有对应场景**；
- 无场景的能力不引入，可注明「不适用」及原因。
