# HD-1910：1 Mbps → 500 kbps 到底有什么影响（2026-11-09）

> 背景：台架 ID10 出厂 `reg6 = 0`（1 Mbps），B 代 robotd 部署线要求 `reg6 = 1`（500 kbps）。
> 用户问「1M 变 500k 会有影响吗」。本轮**零 EEPROM 写操作、零硬件写入**，只跑了只读预算脚本
> （顺带重测了一次 1M 单舵机），其余全是源码/资料查证。

## 0. 一句话判决

**不改变舵机、不改变策略、不需要重训；唯一实质影响是每 tick 的线上时间正好翻倍**
（4.13 ms → 8.26 ms 纯传输），把 50 Hz 环留给推理的余量从 ~13 ms 压到 ~9 ms，最坏档只剩
~2.5 ms。**50 Hz 仍然装得下，但「不出错」的余量变薄了** —— 这才是要盯的地方。

## 1. 不变的部分（带一手证据）

| 项 | 为什么不受波特率影响 | 证据 |
|---|---|---|
| 控制周期 50 Hz / obs 61 / act 14 / 策略权重 | `BAUD_RATE` 只用于打开串口；周期由 `[control] hz` 与 ticker 决定，策略是 ONNX 图上的数 | `feetech.rs:301` `serialport::new(port, BAUD_RATE)`；`obs.rs:50-59` 宽度是编译期常量 |
| 力矩 / 转速 / 位置环增益 / 编码器 4096 / 0.732 rpm | `reg6` 只管通信；RAM 控制寄存器（44 电流、46 速度、41 加速度、50/51 Kp/Kd、40 扭矩）**每次上电由 robotd 自己写**，跟波特率无关 | `feetech.rs:393-397`；`out/robotd_hd1910_mode0.toml:30-31` 明写「NOT install steps」 |
| 每 tick 字节数 413 B | 帧长由协议与寄存器布局决定（16 设备 × 15 B、15 个写 ID），不是速率 | `probe_bus_budget.py` A 段本轮真跑：`sync_read` 发 24 收 336，`sync_write` 发 53 |
| 观测采到的是「哪一拍」 | 只要读在同一 tick 内完成，波特率不改变观测的时间戳；训练侧 IMU 延迟包络 0–20 ms | `microduck_velocity_env_cfg.py:564`；软件方案 §12.4 |
| ⇒ **不需要重训** | plant（机构/动力学/动作空间）没变，换的只是通信速率。项目里「换 plant ⇒ 必重训」不触发 | 软件方案 §8 纠错备案 / 记忆准则 |

⚠️ **一条是推的，不是查实的**：飞特官方内存表把 `reg7`（应答返回延时）的单位写成 **2 µs**
（时间单位，最大 254×2 = 508 µs），而 `check_registers()` 不写 reg7、保持出厂 0=最小延时
⇒ 推断「降波特率不会让每颗舵机的响应等待也翻倍」。但 **HLS 的 reg7 语义没有在本项目源码里
逐字确认**（查到的内存表是 SMS/SCS 文档），标 🟡 推断，别当结论用。
`bus.rs:129` 那个 `return_delay_time = 250` 吃掉 40% tick 是 **XL330/Dynamixel 路径**，不是飞特。

## 2. 变的部分：线上时间翻倍（本轮真跑，非手算）

命令：`python tools/hd1910/servo_probe/probe_bus_budget.py`（`--selftest` 25/25 通过）。
硬件 COM3 / ID10 在线，C 段是 **1 Mbps 单舵机实测**；D 段是**无量纲比值外推**到 500k/16 设备。

| 段 | 读数 |
|---|---|
| A 静态 | 413 B/tick（读 16 设备：15 关节 + IMU 200；写 15 ID） |
| **B 纯传输** | **1 Mbps = 4.130 ms（21% 周期）**；**500 kbps = 8.260 ms（41%）** —— 8N1 下每字节 10 bit，正好 2× |
| C 台架 @1M | ping min 215.5 µs / read2 252.8 µs / read15 405.8 µs；差分 13 B = 153.0 µs ⇒ **11.77 µs/字节**（理论 10.00，比值 **1.18**）；固定开销 64.5 µs/包（含 USB 批延迟，**不可**按设备数外推） |
| D 外推 @500k | 基准 23.54 µs/字节（= 20 µs 理论 × 1.18）；gap 50/100/200/500 µs ⇒ 每 tick **10.33 / 11.13 / 12.73 / 17.53 ms**，占 20 ms 的 **52 / 56 / 64 / 88%**，余量 **9.67 / 8.87 / 7.27 / 2.47 ms** |

⚠️ **证据等级（R11）**：C 是 1M 单设备实测，D 是**比值外推**，不是 500k 直测。
本轮读数（11.77 µs、10.33–17.53 ms）与 2026-11-04 文档 §11.4 那轮（11.5 µs、10.12–17.32 ms）
有轻微抖动，属不同轮次实测差异，**量级一致**；跨轮数字不要混用。

### 2.1 上游注释的「7.5 ms」和这里的「10.9 ms」不矛盾（两条独立算法）

`feetech.rs:14` 写 *"A 16-device read costs ~7.5 ms of a 20 ms tick"*，`feetech.rs:117`
重复一次。用另一条算法核：纯读 = 24 + 336 = **360 B**，@500k × 10 bit = **7.20 ms**
⇒ 与 7.5 ms 吻合。所以上游那个数是**不含 gap、不含固定开销、不含写帧的纯传输**。

项目 D 段的 11.13 ms = 纯传输 8.26 ms（含写） + 16×100 µs gap 1.6 ms + 1.18× 实测校正 +
USB 固定开销。**差异是口径，不是矛盾**；两个来源对同一个「纯传输」量独立算得一致。

### 2.2 1M 侧对照（用另一条路径独立算）

软件方案 §11.5 给过 1 Mbps 中心估计 **6.79 ms/tick**（gap 100 µs）。本轮：纯传输 4.13 ms
+ gap 1.6 ms + 固定开销约 1.0 ms ≈ 6.7 ms ⇒ 吻合。

⇒ **降速代价 ≈ +4.1 ms/tick（中心档）**；余量 13.2 → 9.1 ms，最坏档 2.7 → 2.5 ms。
最坏档已经吃掉 20 ms 周期的 88%。

## 3. 真正的风险不是「慢」，是「掉出 50 Hz 环」

这几条都不报错，症状是 `achieved_hz` 掉下来：

- `update_gate.min_achieved_hz = 45`（50 Hz 的 90%）⇒ 低于就判 **unhealthy**，
  updater 语义是**自动回滚 release**（`main.rs:726`）。一个总线预算问题看起来像发布系统故障。
- ticker 是 `MissedTickBehavior::Skip`（`main.rs:1481`），丢掉的周期**不补**。
- `READ_TIMEOUT = 30 ms`（`feetech.rs:118`）**比一个周期还长** ⇒ 一次读超时直接吃掉整 tick。
- rustypot `sync_read` **逐 ID 阻塞读且顺序强制**（`dynamixel_protocol/mod.rs:712`），
  IMU（ID 200）排在最后 ⇒ 策略最需要的 gravity 是这一串里最晚到的；写前
  `flush_if_needed` 最多 3 次 × 5 ms（`mod.rs:760`）⇒「越错越慢」的正反馈。见软件方案 §11.6。
- **训练侧后果**：`imu.rs` 注释写明走路策略在 IMU lag 超过 ~20 ms 就失败（BAM 仿真
  2026-10-10），而训练给的延迟包络是 0–20 ms。⇒ 500k 只要不超时，obs 分布不变；
  一旦丢 tick/重试，就叠加**整拍**延迟超出包络 ⇒ sim2real 错位。

⇒ **降速本身不改策略，改的是「不出错」的余量**。这也正是 Pi4B 完整方案 N2 否决 USB 的理由：
最坏档只剩 2.5 ms，USB CDC 额外几毫秒几乎必然把环顶到 45 Hz 以下（该文档 §5）。

## 4. 反而变好的部分

- **位宽 1 µs → 2 µs**，长线 / 噪声 / 半双工换向的容限更宽。🟡 外部通用经验
  （`bb_servo_feetech` 配置文档：*"Higher baud rates enable faster polling but may be less
  reliable with long cable runs or electrical noise"*）——通用资料，**非本项目实测**。
- **板载 UART 能精确分频**：A733 `24 MHz/16/3`、Pi 4B `48 MHz/16/6`（算术推导，位宽待示波器）。
  在 A733 上要 1M 会实际得到 **750 kbps**、没有任何舵机听得懂 ⇒ 对那条线来说
  **500k 是修复而不是退化**（`feetech.rs:12-14`、上游 `tools/servo/set_baud.py:4`）。
- 记忆里 SCS15 手册记 500000 档误差 0.000%，本轮**未重查**，标存档值。

## 5. 落地代价（不改代码，改 EEPROM 与工具口径）

1. **不是只改一颗舵机**：整条总线 16 个设备统一 500k。IMU 从机固件
   `main.rs:345-346 proto_baud() = 500_000`、`proto.rs:246 6 => 1 // 500 kbit/s`。
2. **开机硬校验 checked-not-corrected**：`feetech.rs:386-391` 读 `reg6`，`!= 1` 直接
   `servo N is not configured for this robot`，**总线根本不打开**。出厂 0 ⇒ 上板必改。
3. **EEPROM 时序按本项目实测**：断电 → 解锁 55=0 等 0.25 s → 写等 0.50 s → 上锁 55=1 等
   0.50 s → 再断电回读（2026-11-04 在这颗 ID10 上两次断电复现）。**回读 PASS ≠ 持久 PASS**。
4. **所有台架工具默认 `--baud 1000000` 都要换 500000**（切过之后）；编码是 Feetech
   `0=1M / 1=500k`，⚠️ 别套 `model.rs:177` 的 Dynamixel `baud_rate = 3`（§11.5 的陷阱）。
5. **与「台架不切」不冲突**（用户 2026-11-09 拍板，Pass53）：台架保持 1M 是**当前调试口径**；
   上板逐颗写 `reg6=1` 是**部署阶段本来就要做的步骤**。R3 的自指风险只出现在「用 URT-2
   去验 500k」时；换板载 UART 绕开的是 CH343/USB CDC 那条**路径**，不是 500k 本身。

## 6. 🔴 代次边界订正（查全：两条线别当成同一个「我们」）

软件方案 **§9.1:1321-1328** 与 **§11.5:1497-1526**（2026-11-04）写：
> 「正确动作是把 `BAUD_RATE` 改到 1 Mbps… **15 颗舵机的 EEPROM 一颗都不用写**」

这条推导的前提写在原文里：「**我们要用的 Radxa Zero 3W（RK3566）**」+ 上游主仓
`pollen-robotics/microduck` 的 **1 Mbps 线**。它对应的是 `hd1910m` / FT-SCS 原生那条
（Radxa、`scs`/`feetech.rs` 1M、不查那四个 EEPROM、验固件元数据 `row[33]==4`）。

**当前部署主线不是那条**：`out/robotd_hd1910_mode0.toml:15-29` 逐字写明
「There is no `baud` key」、速率编译在 `feetech.rs:35 BAUD_RATE = 500_000`、
「Ours ship at index 0 (1 Mbps)… **Move each one with** `hd1910_ident.py baud`」，
以及开机硬校验 `reg6 = 1 <- must change`。⇒ **B 代 `DuckBuddy-main` / HL-2915 /
`feetech_hls` 线必须逐颗写 `reg6=1`**，不能引用 §11.5 当成「不用切」的依据。

顺带一条口径：**G0 闸门「50 Hz 事务 ≤5 ms」**（软件方案 :390）是 **P0 台架 @1 Mbps**
的验收标准；500k 下光纯传输就 8.26 ms，这条闸门**不能照搬**到部署线（R11 的又一实例）。

⇒ 已在 §9.1 订正块与 §11.5 标题下加 2026-11-09 代次标注，**原文一字不删**（留证据链）。

## 7. 边界 / 本轮没做的

- **零硬件写操作、零 EEPROM 操作**；台架 ID10 仍是 `reg6=0`/1M，探针默认 `--baud 1000000` 不变。
- 未测 **500k 真机 16 设备**（需 15 颗 + IMU 上板）；未测位宽精度（需示波器/逻辑分析仪）；
  未测策略推理在目标板的耗时；未验自动方向板在 500k 的误码率。
- **所有 500k 数字都是比值外推**，不是直测。R3（CH343 @500k 是否真发帧）**仍未消**，
  消项条件见 Pi4B 完整方案 §12.1 决策块。
- 现状不变：台架 PC + URT-2 + 单舵机，软件 0 成本，**别买板**。
