## 0. 一句话结论

**有可优化点，而且其中一条（`/etc/fstab` 的 `defaults,,commit=120`）被同类嵌入式 Armbian 实现逐字命中过；但按开发规范与本项目现状，本轮结论是「逐项落档 + 分级建议，不实施任何镜像改动」。** 原因是三条硬约束同时成立：① 镜像是上游既定底座，任何 rootfs 改动都会破坏已验证的 sha pin / 可复现链（`image_pairing_contract.json`、`card_build_contract.json`）；② 当前**没有实机全量验证手段**（串口 CH343 处于 phantom 状态、无 HDMI 接入、整机未落地、板子丝印版本未确认）；③ 开发规范 §3.2 要求内部改进「不得改变用户可见行为与接口契约」、§6.2 要求「每完成一项改动必须全量验证」、§7.4「无场景不引入」。⇒ **发现即记录，实施留到有整机 + 有验活通道之后**，符合 §6.3「状态真实、不虚报」。

> 📌 **当前态判断（规范 §7.4）**：项目软件线已饱和，唯一杠杆是整机落地；镜像优化**不是当前瓶颈**。本轮价值在「把候选、依据、边界钉死」，不在「马上改」。

## 3. 优化候选与分级判决

图例：**证据强度** = 一手页面/源码实访 ＞ 多源一致 ＞ 社区单源 ＞ 推断。 **判决**：`可考虑(零风险)` / `暂不实施` / `无场景` / `需用户拍板`。

### 3.1 健壮性

| # | 候选 | 依据（多方印证） | 边界与判决 |
|---|---|---|---|
| 1 | **`/etc/fstab` 的 `defaults,,commit=120,errors=remount-ro`**：双逗号 + 120 s 提交间隔 | ① `fstab(5)`（man7 页面实访）：第四字段 "formatted as a **comma-separated list of options**"，**未定义空选项语义** ⇒ 双逗号最多算无规范依据的写法；② Linux 内核文档 `admin-guide/ext4`（kernel.org，逐字原文）：`commit=nrsec` **默认 5 s**，"if you lose your power, you will lose as much as the latest 5 seconds of work…Setting it to very large values will improve performance"；③ LKML 提交 `23f6b0240534`（Jan Kara / Theodore Ts'o）澄清语义为 "limits the maximum age of the running transaction"，并补「延迟分配下更旧数据也可能丢」；④ **同类设备逐字命中**：社区 `FranckFG62/J1s-Klipper-Macros/Armbian_Optimisations_EN.md`（962 MB RAM 的 Armbian 26.2.1）原文 "`commit=120` (2 min) in the original fstab: too long, risk of data loss on power failure. **Double comma `defaults,,` in fstab (cosmetic bug, also fixed)**"，修法 `defaults,noatime,commit=60,errors=remount-ro`；⑤ 多源调研综合结论亦建议边缘设备 `commit ≤ 60 s` | **证据最硬的一条**（一手手册 + 内核文档 + 内核提交 + 同类实现逐字命中 + 多源综合）。但改 fstab 会改 rootfs ⇒ 破坏 sha pin，且 `fstab(5)` 明写改完必须 `systemctl daemon-reload`、开机行为需实机验证（当前无通道）。⇒ **`暂不实施`，列为「拿到整机后的第一优先」**；不擅自把 120 改成 60，也不声称双逗号会导致启动失败（一手手册无此定义） |
| 2 | `mediad` / `tofd` 在裸板无摄像头/ToF 时反复崩溃重启 | 镜像内 `mediad.service` 注释自陈：「camera being on by default…a robot whose camera is absent…fails to start this service and loses its WebRTC control surface」；执行单/脚本头注已把该崩溃列为**已知预期**；freedesktop `systemd.unit(5)` 页面实访（AI 摘要超时，仅取到前 15k 字符，**未取到 `ConditionPathExists=` / `StartLimitBurst=` 目标段落** ⇒ 具体默认值不引用，只作机制级参考） | 项目订正㉑ 明写相机/ToF **必需不可砍**，加条件启动会改变既定服务行为；且缺一手段落，不做具体参数建议。⇒ **`暂不实施`**（等整机接上真实相机/ToF 再谈） |

### 3.5 与安卓 App 互相适配（用户追加维度）

**核查方式**：镜像侧只读实读（服务清单 / unit 注释 / `architecture.md` 端口表） ↔ App 侧项目一手（`microduck-android-app/README.md`、源码、C2/P1 门禁脚本）。

| 项 | 镜像侧实读 | App 侧契约（项目一手） | 适配结论 |
|---|---|---|---|
| BLE 传输 | `btd.service`（"BLE front door onto the robot API"）+ `dbus-org.bluez.service`；**保持 UNPRIVILEGED**；注释明写 `hci0` 上电后约 **73 s** 才出现（AIC8800 UART 挂载晚 + bluetooth.service 被 dbus 阻塞约 26 s），`padd.service` 注释独立二次印证同一 73 s | App `BleTransport` + `AndroidBleGattLink`；README 明写 **真机 GATT bonding/CCCD/`onCharacteristicWrite` 时序未上板验证**，仅 JVM `FakeGattLink` 测过；`hello` 带 `api_version` → `system.authenticate`（v4 起 BLE 必过） | ✅ **对端存在**，但存在**硬时序约束**：上电后 ~73 s 内 BLE 不可用。⇒ 这是 **App 侧需要等待/重试策略**的设计约束，不是改镜像能解决；判 **`需上板联调`**，且应写进 App 的连接状态机与真机验收清单。**两条独立 unit 注释互证 73 s**（准则 3） |
| UDP netpad 驾驶 | 镜像侧**未找到** `:4210` / netpad 配置；`padd.service` 是蓝牙手柄 intent client（不是 netpad 服务端） | App 真机驾驶 = UDP netpad **28 B wire / `:4210`**；README 写「板上 `service.sh netpad on` 后验证 UDP 驾驶方向与 250 ms timeout」；P1 只在 JVM 真 UDP socket 上验过，**真固件是 B 代 API16、没有 netpad** | ⚠️ **适配缺口（未闭合）**：App 的驾驶主通道在镜像里没有已确认的服务端。⇒ **`需上板核 `service.sh netpad on` 是否存在 / 谁监听 4210`**；在证实之前不得声称「App 能驾驶这块板」 |
| JSON-RPC / API 版本 | 镜像内仅在 `updater-design.md` 把 `API_VERSION` 当概念提及，**未找到具体值**；`robotd` drop-in 指向 `/etc/robot/feetech-ft5/robotd.toml`（`port=/dev/ttyS2`、`hz=50`） | App 对接目标 = fanhao fork **API40**；`robot.subscribe` ≠ `robot.state`、错误码 14 / -32601 / -32602、能力靠 -32601 降级；执行单 2.5 要求 control.40→.43 升级后**上板版本回读 `BA-X-1`** | ⚠️ **版本链未闭合**：镜像静态文件给不出 API 版本，必须上板 `hello` 回读。⇒ **`暂不实施 / 等 BA-X-1`**，不猜版本、不改契约 |
| WebRTC / 视频 | `mediad`：`:8080` console + `GET /frame`、`:8443` signalling、`/run/mediad/media.sock` | App `WebRtc` 后端属 **P2 视频，尚未实现**；四后端中 Mock/Tcp/Ble 已落地真测 | ⇒ **镜像超前、App 未接**，属规范 §7.4「无场景不引入」：**不为它改镜像**；等 App 侧 P2 拍板再谈 |
| `body_server :7801` | 镜像侧无此服务 | App C2/C2+ 的 `0.0.0.0:7801` 是 **Windows MuJoCo 仿真体 + WSL `robotd --sim`** 的台架通道（README §C2+、`c2_body_server.sh`） | ⇒ **明确排除**：不要把它当成镜像应开放的端口，也不要据此加服务（准则 12：先判来源再谈缺口） |

**这一维的总判决**：**不建议为「适配 App」改镜像**。真正缺的是三件事——① App 侧 BLE 连接要容忍 ~73 s 适配器就绪；② 上板确认 netpad `:4210` 服务端与 `service.sh netpad on`；③ 上板回读 `hello` 的 api_version 与 `BA-X-1` control 版本。三者都是**上板联调项**，不是镜像内容优化；写进 `docs/active/microduck-安卓App-整机落地验收清单-2026-11-13.md` 的待办即可。

## 5. 明确排除项（规范 §7.4 无场景不引入）

- ❌ 为 App 开放 `body_server :7801`：那是台架仿真通道，不是镜像服务。
