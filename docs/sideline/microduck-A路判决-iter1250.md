## 这两个 bug 的解剖

用户问「怎么还有 bug，不是有官方参考吗」。必须分清两类，因为它们的成因完全不同。

### Bug A：世界系 vs 体坐标系（语义差，参考里有，但我没用上）

评测脚本里

```python
net = xy_t[-1] - xy_t[0]          # root_link_pos_w -> WORLD frame
dx_mean = net[:, 0].mean()
```

而命令是**体坐标系**速度。`velocity_env_cfg.py` 的 `reset_base` 事件里明明写着：

```python
pose_range = {"x": (-0.5, 0.5), "y": (-0.5, 0.5), "z": ..., "yaw": (-3.14, 3.14)}
```

**初始朝向在整个圆周上均匀随机。** 于是各 env 的世界系位移互相抵消，`dx_mean` 必然趋近 0
——哪怕每一个机器人都在从自己的起点走开。实测 `dx_mean −0.039 m`、`|dy|` 中位 0.878 m，
看起来像「原地打转 + 横着滑」，实际是坐标系错位。

这个文件我读过、还改过它下面一行（`pose_range["z"] = (0.12, 0.13)`），却没注意 yaw。
**「有参考」救不了这种 bug，因为 bug 在我写的那一行，而不在我查的那份文档里。**

修复：把每个 env 的位移投影到**它自己的初始朝向**上，同时给出体坐标路径长度 ∫vx dt 作交叉校验。

| | 修前 | 修后 |
|---|---|---|
| dx | −0.039 m（世界系） | **+1.575 m**（体坐标投影） |
| \|dy\| | 0.878 m | 0.530 m |
| ratio | −0.01 | **0.55** |
| `translates_forward` | FAIL | **PASS** |
| `not_sideways` | FAIL | **PASS** |

### Bug B：补丁里漏了 `import os`（纯手误，参考无关）

`microduck_velocity_env_cfg.py` 顶层没有 `import os`，我在追加的块里直接用了
`os.environ.get(...)`，一 apply 就 `NameError`。

这个 bug 与「有没有官方参考」完全无关，它是漏写一行。

**但它是被验证机制当场抓住的**：apply 之后我立刻跑了「不设环境变量 / 设 =1」两遍对比，

## 为什么这次能发现，而有些 bug 发现不了

判据不是「结果对不对」，而是**两个来源是否互相矛盾**：

- 这次冲突：体坐标 `vy = +0.016 m/s`（几乎没侧移）**却**世界系 `|dy| = 0.878 m`。
  两个都合理，但不可能同时成立 → 一定是口径错了。
- 前一天 joy 的结论「原地踏步」：净位移 14 mm **和**体坐标 `vx = −0.001 m/s`，
  **两条独立路径同向** → 结论成立，那个判断没有受这个 bug 影响。
- 拿不到冲突时才是危险区：静默 bug 的特征是输出落在「看起来合理」的区间
  （`−0.039 m` 像「没走」、`0.878 m` 像「横着滑」）。所以凡是坐标系 / 单位 / 轴的量，
  必须用**两条独立算法算同一个量**并比对。

## 更正：旧读数符号是反的（2026-10-25 14:30）

### 起因：里程碑守候报「变好」，但速度掉了

`watch_milestones.py` 按原规则报 iter 4000 `improved`（误差 −10.1%），于是训练继续跑 12000。
可同一份结果里 vx 从 0.258 → 0.209（−19%）、每脚落地 2.13 → 1.40 Hz（−34%）。
「误差降了」和「走慢了」是同一件事，原规则只看 `error_vel_xy`，把退化判成了进步。

### 追下去：`error_vel_xy` 低于自己的算术下界

`_update_metrics` 的定义是 `mean ||cmd_xy − v_xy||`（`velocity_command.py:61-69`），
所以它必然 ≥ `|cmd − mean(vx)|`。iter 4000 实测 **0.174**，而 `|0.4 − 0.167| = 0.233`
——**读数低于下界**，说明分母里有东西不是我以为的那个。

逐层排除后抓到：`freeze_command()` 确实把 `rel_standing_envs` 设成 0，但 cfg 里还有一个
`standing_envs` 课程项，**每一步**按 `common_step_counter` 重写这个字段
（`mjlab_microduck/tasks/mdp.py:3440-3474`，分级到 `2000*24` 步 = **0.25**）。
而让评测可复现的做法正是把计数器钉到 1e9（= 所有课程取末级）⇒ 每次评测都有 25% 的 env
被命令「站着」，误差≈0 混进均值；25% 又是按 env 独立抽的（32 个里 6–10 个），
**稀释比例每次不同**，两次评测的差值就被读成了「进步」。

实测证据：`PROBE after build: rel_standing_envs = 0.25  is_standing = 6 ... of 16`，
`PROBE cmd x uniques: [0.0, 0.4]`。

### 修法（两条，必须同时）

1. `freeze_command()` 里 `cfg.curriculum.pop("standing_envs", None)`——只改 cfg 值没用，下一步课程又写回去；
2. 把协议变成闸门：记录每步 `vel_command_b`，新增 `command_frozen_ok`（`max|cmd − frozen| ≤ 1e-3`）。
   **负对照**：去掉 `pop` 重跑 → 该项立刻 FAIL，打印 `uniq vx [0.0, 0.4] / frac cmd==0 25.0%`。

### 教训

**「我设了这个字段」不等于「这个字段还是这个值」。** 只要还有第二个写者（课程、manager、
reset 事件），冻结就必须**可测量**（记录 + 闸门），不能是声明式的。
这次的代价：一个反了符号的结论 + 差点为「变慢」再付 5 小时 GPU。
而抓到它的不是「再多看一眼图」，是**算出一个下界**——读数和下界矛盾时，错的一定是读数。
