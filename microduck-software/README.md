## 客观评估（比看视频可信）

```bash
cd microduck-software
./.venv/Scripts/python.exe tools/eval_policy.py --command 0.4,0,0 --seconds 8 --envs 16
```

它跑 16 个独立 rollout，报告**实测速度、跟踪率、摔倒数**，而不是靠肉眼判断"看起来在走"。
`--json` 输出单行，方便批量扫描和前后对比。

单个条件不够——真正的问题是"能跟到多快"。`tools/envelope.py` 扫 19 个命令点：

```bash
./.venv/Scripts/python.exe tools/envelope.py \
  --policy repo/microduck_policy.pt --policy out/deploy61.pt --envs 12 --seconds 12
```

**56 维（仓库预训练）vs 61 维（本目录训练）不是"谁更好"，是能力形状不同：**

| 命令 | 56-D 跟踪率 | 61-D 跟踪率 |
|---|---|---|
| +0.30 m/s | 0.776 | 0.706 |
| +0.50 m/s | 0.555 | **0.883** |
| +0.60 m/s | 0.177 | **0.883** |
| +0.70 m/s | 0.048 | **0.625** |
| −0.30 m/s | **0.960** | 0.935 |
| 侧移 +0.10 / +0.20 | 0.679 / 0.770 | 0.742 / 0.622 |
| 侧移 −0.10 / −0.20 | 0.486 / 0.002 | 0.304 / 0.241 |
| 转向 +0.30 / +0.60 / +0.90 | **1.14 / 1.08 / 1.05** | 0.78 / 0.88 / 0.93 |
| 通过点数 | 15/19 | 15/19 |

两个都过 15/19。56 维转向明显更强，61 维在中高速前进（+0.60 差 5 倍）和双向侧移上更强。

两个都被量出同一个真实短板：**+0.10 m/s 跟不动**（0.46 / 0.93）。步态有一个最低速度，
低于约 0.15 m/s 的命令实际上是在原地踏。真机上要么给摇杆加死区，要么在奖励里补低速整形。

## 自己训练

```bash
cd microduck-software/repo

# 可部署版本（61 维观测，与官方 duck-control 契约一致）
../.venv/Scripts/python.exe train_official.py \
  --num-envs 4096 --iterations 1500 --timestep 0.005 --out ../out/deploy61.pt

# 原始版本（56 维，仅供对照，不可部署）
../.venv/Scripts/python.exe train_ppo.py \
  --task velocity --num-envs 4096 --iterations 1500 --timestep 0.005

# 在"真实环路"里微调（两段课程，务必先小后大）
# 阶段 A：只加动作延迟，学一个控制周期的容忍度。lr 必须降下来，热启动用 1e-3 会在 16 轮内崩。
../.venv/Scripts/python.exe train_robust.py --num-envs 4096 --iterations 250 \
  --init ../out/deploy61.pt --act-delay 0,1 --obs-delay 0,0 \
  --lr 2.5e-4 --epochs 3 --out ../out/robust61_a.pt
# 阶段 B：加到目标随机化，并把关节速度滞后做成逐环境概率（见下）
../.venv/Scripts/python.exe train_robust.py --num-envs 4096 --iterations 250 \
  --init ../out/robust61_a.pt --act-delay 0,2 --obs-delay 0,1 --jvel-lag 0.5 \
  --lr 2e-4 --epochs 3 --out ../out/robust61.pt
```

三个参数值得单独说，都是踩过才知道的：

- **`--lr` 热启动必须降到 2e-4 ~ 2.5e-4，`--epochs 3`。** `train_ppo.py` 默认的 `LR=1e-3,
  EPOCHS=5` 是给从零学走调的；对一个已经会走的策略，16 轮内 reward 从 3.71 掉到 −0.35。
- **`--sigma` 和 `--track-weight` 都不是好旋钮。** 前者同时改变区分度和尺度，后者改不了
  区分度；而且 `--track-weight` 只乘 `track` 不乘 `turn`，会把转向的相对权重悄悄压掉。
  见"负结果 4"。真要改，用 `--track-baseline`。
- **`--jvel-lag` 是概率不是开关。** 设成 1.0（也就是上游固件的真实行为）训出来的策略会
  反过来依赖这个滞后：有滞后 0.246 m/s、没滞后 0.124 m/s。别人自己编译 `duck-control`、
  或固件直接报真速度时，速度就砍半。0.5 让两个世界都见过，且不影响最终成绩。

56 维之所以"仅供对照"，有两个独立原因，不是一个：观测里有 `base_lin_vel`（真机测不到，
上游是显式删掉后放进 critic 的），还有最后两维是 `sin(clock)` / `cos(clock)`——**步态时钟
本身被塞进了观测**。`duck-control/src/obs.rs` 的 61 维契约里没有这个通道，所以 56 维策略
在真机上连输入都凑不齐。这两点经常被混成一句"56 维用了特权信息"，实际是两件事。


`--timestep 0.005` 不是笔误：CPU 的代价是 `mj_step` 调用次数，不是仿真秒数。把物理步长从
0.002 放到 0.005（200 Hz），接触精度略降，吞吐提高约 2.5 倍，控制环仍是 50 Hz。

## 导出 ONNX

```bash
./.venv/Scripts/python.exe tools/export_onnx.py \
  --policy out/deploy61.pt --out out/deploy61.onnx
```

导出的是 actor 的**均值动作**（不是采样），并且把观测的 running mean/var **烘进计算图**。
脚本会用 onnxruntime 跑同一批观测与 PyTorch 对比，差异超过 1e-4 直接判失败——因为
"归一化没进图"这个 bug 在仿真里是完全隐形的。

部署侧约定（来自 `duck-control/src/obs.rs`）：输入名 `obs`，形状 `[1, 61]`；输出 `[1, 14]`；
`ctrl = stand_pose + ACTION_SCALE * action` 这个偏移刻意留在图外。

## 部署到 MCU：一块 ESP32 够不够

**够做控制环，不够做视觉和对话。** actor 是三层全连接，实测：

```
weights     26376 float32 = 103.0 KiB flash
compute     25984 MACs per forward
            ESP32 / S3 @240MHz: 0.54 ms  (2.7% of a 20 ms period)
            ESP32 @160MHz:     0.81 ms  (4.1%)
```

2.7% 的控制周期意味着这块 20 元的 MCU 跑策略毫无压力——瓶颈从来不在算力。

```bash
./.venv/Scripts/python.exe tools/export_mcu.py \
  --policy out/robust61_a.pt --out out/mcu
```

产出 `out/mcu/policy.h`（纯 C99，只依赖 `<math.h>`）和 `out/mcu/selftest.json`。
不用 ONNX 是因为 ONNX 需要 runtime，而这里只有三层稠密层，手写 C 比任何解释器都小都快，
且没有依赖。

### 为什么这个脚本要自己实现一遍前向

torch 在 x86 上用 BLAS 求和，累加顺序和 MCU 上的 `for` 循环不同，直接比等于把误差藏起来。
所以脚本里有一个 `seq_forward`，用 `cumsum([bias, t0, t1, ...])` 精确复现 C 的从左到右累加，
报告的是 torch 与**同顺序实现**的差：

```
literals    26376 emitted, all round-trip bit-exact
float32 accumulation order gap vs torch: 3.81e-06
```

两件事分开验证：字面量从生成的文件里正则读回来逐位比对（26,376 个全部 bit-exact，
这抓的是 `%.9g` 精度丢失和 `carray()` 自身的 bug）；累加顺序差 3.8e-06（这抓的是
"MCU 的 float32 和 torch 不是一个网络"这个假设到底差多少）。

### 一个会静默出错的布局细节

61 维观测的最后 13 维不是"命令 + 填充"：

| 区间 | 内容 | 部署时给什么 |
|---|---|---|
| `[48..51)` | 速度命令 vx, vy, vyaw | 摇杆 / 策略输入 |
| `[51..55)` | **头部命令**（4 维） | **对应我们这份权重必须全 0** |
| `[55..61)` | **身体姿态命令**（6 维） | **对应我们这份权重必须全 0** |

**"必须全 0" 只对这份权重成立，不是布局的属性。** 同一条 13 维命令块
`[twist(3), head_pose(4), body_pose(6)]`，不同训练任务对后 10 维的处理不一样：

| 来源 | `head_pose[0:4]` | `body_pose[0:6]` |
|---|---|---|
| 我们的 `robust61_a.pt` | 训练时恒 0 | 训练时恒 0 |
| `HannesVonEssen/microduck-running`（HF，1.651 m/s） | 模型卡写明 **unused; zeros** | **unused; zeros** |
| 上游 `microduck_velocity_env_cfg.py` | **是训练目标**：`UniformPoseCommandCfg` 每 2–5 s 重采样，`std=0.5`，`head_pose_bias` 课程 iter 600→1500 | 类似 |

所以三件事要分开说：

1. 我们这份权重喂非零值会离开训练分布，而网络**仍然会输出一个看起来合理的动作**——
   验证时看不出来，真机上表现为"走得怪"。这是必须全 0 的**唯一**原因。
2. 社区那份跑步权重同样全 0，与我们的结论互相印证。
3. **但上游 env 是把 head_pose 当正式目标的**。我们的权重没有头部能力，不是因为这个布局
   不支持，也不是因为上游没做，而是我们的训练配置没把这一层搬进来。要真做头部跟踪，
   得先在自己的 env 里补 `head_pose` 命令项并重训，不是部署时填进去就行。

另一条从 `microduck-running` 模型卡里学到、和我们不同的设计：它的速度目标是
**奖励前进、可以超过命令**（"`twist[0]` is not a hard speed limiter"），而我们的
`exp(-(v-cmd)²/σ)` 是双向对称的惩罚。前者更容易冲出速度前沿，后者更容易退化成站着
（见后文"奖励分不清站着和走"）。

### 输入合理性检查：`md_obs_ok()`

上游 `safety.rs` 只拒绝非有限的动作。这能抓住报 NaN 的 IMU，抓不住更常见的失效：
传感器掉线后**报 0**。零陀螺和零重力都是合法浮点数，而机器人直立时投影重力不可能是零
（模长恒为 1）。`md_obs_ok()` 因此额外检查 `|g| ∈ (0.5, 1.32)`，窗口宽到容得下训练时的
重力噪声（σ=0.01，实测 |g| 在 1.00±0.02 内），窄到能抓住全零或乱码。

这条不是假想：导出时的 `stress_fall` 自检向量（陀螺 4 rad/s、关节速度 8 rad/s——跌落时都
真实可达）让网络输出了 **|action| = 11.0 rad**。SafetyLayer 会把它裁到 ±π，但那是事后补救；
在输入端拦住更便宜。

### 真的编译过——但用的是别人的 C 编译器

这台机器上没有 MSVC 也没有 gcc。`pip install ziglang` 没有可用版本（本机 Python 3.13 太新），
于是从 `ziglang.org` 直接下 0.13.0 的 zip 解到 `bin/zig/`——zig 自带 `clang`，

```bash

```

结果（`policy.h` + `selftest_vectors.h`，`-std=c99 -O2 -Wall -Wextra`）：

## 奖励分不清"站着"和"走"——这是最难发现的一类失败

`train_ppo.py` 的速度跟踪项是

```python
track = exp(-sum((v_xy - cmd_xy)**2) / SIGMA)      # SIGMA = 0.25
```

代进去：命令 0.3 m/s、机器人**站着不动**（v=0），`exp(-0.09/0.25) = 0.698`。

也就是说 `track` 这一项对"完全站着"给 0.698 分。而其他项——`gait` 0.83、`upright` 0.99、
`pose` 0.89、`height` 0.49——**全都奖励"稳稳站着"**。于是站着不动的总分和正常走的总分只差
不到 0.15。

这件事的后果我们实测到了两次：

1. 日志里 `track 0.83` 看着像在走，实测速度只有 0.085 m/s（真实在走的话 track 应该接近 1.0）。
2. 把动作/观测延迟和关节速度随机化加进训练后，总分从 3.84 掉到 3.71（看起来"只是稍微难了
   一点"），实际速度从 0.127 m/s 掉到 0.085 m/s，**策略在低学习率下顺坡滑向"站着别动"这个
   更安全的局部解**。摔倒数还是 0，倾角还是 4.5°，所有健康指标都正常。

**`SIGMA = 0.25` 不是上游值。** 我们一直这么以为（代码注释里甚至写着 "upstream 0.25"），直到
这一轮直接去读源码：上游 `microduck_velocity_env_cfg.py:343` 是 `std = math.sqrt(0.1)`，而
mjlab 的公式是

```python
return torch.exp(-lin_vel_error / std**2)     # mjlab/tasks/velocity/mdp/rewards.py
```

也就是分母 **0.10**。我们的 0.25 比上游**宽 2.5 倍**，站着不动对 0.3 m/s 命令拿 0.698，
上游只拿 0.407。

更严重的是另一头，而且这个错是我们独有的：上游的**角速度**核是 `std = sqrt(0.5)`，分母
**0.50**，而我们让 `turn` 和 `track` 共用了同一个 0.25。yaw 误差的单位是 rad/s，实际动起来
经常到 0.5–1.0，而那里旧核只剩：

| yaw 误差 | 旧核 0.25 | 上游核 0.50 |
|---:|---:|---:|
| 0.25 rad/s | 0.368 | 0.607 |
| 0.50 rad/s | 0.135 | 0.368 |
| 1.00 rad/s | **0.018** | **0.135** |

误差 1.0 时差 7.5 倍，而 0.018 已经没有梯度了 —— **转向项是饱和的，学不到任何东西**。
这正好解释那个一直没想明白的实验：`--track-weight 3` 之后 `turn` 0.24→0.08、
yaw +0.78→-0.03、"策略完全不转了"。当时归因为"加大 track 权重把转向挤掉了"，真实原因是
转向项早就被窄核压平了，加大 track 只是让本就不存在的项变得更无关。

已改成 `SIGMA_LIN = 0.10` / `SIGMA_ANG = 0.50`，拆成两个参数（`--sigma-lin` / `--sigma-ang`）。
**`robust61_a` 及之后所有历史权重都是 0.25/0.25 训的**，它们从没被正确地奖励过转向。

除此之外还有**权重分配**的问题：`track` 权重 1.0，而 `pose` 0.5 + `upright` 1.0 +
`gait` 1.0 + `height` 0.5 全都在奖励静止姿态（上游 `track`/`turn` 权重都是 2.0，我们分别是
1.0 / 0.5）。在简单植物上这无所谓，策略总会学会走；一旦植物变难，站着就成了更优解。

### 还缺一个 3.0 权重的项：`air_time`

上游行走任务里有 `air_time`，权重 **3.0**（第三大的正项），作用是要求**抬脚时间落在
0.125–0.3 s**。这是"必须真正交替迈步、不许拖脚"的唯一强制力。我们没有这一项 ——
于是拖脚、蹭地、乃至站着不动，都不会被扣分。

把它和上面那个宽 2.5 倍的核放在一起，"站着能拿高分"就有完整解释了，不需要再假设是 DR
把策略打死的。

### 加权重救不了，改 SIGMA 才可能救——两者不是一回事

第一反应是给 `track` 加权（`--track-weight 3`）。它确实把速度从 0.004 拉回 0.132 m/s，
但**超不过不动权重的阶段 A（0.125→0.132 是噪声级差异）**。原因是加权不改变比值：

```
reward ∝ w · exp(-d²/SIGMA)
```

`w` 是乘在整项外面的，所以"站着"与"走对"的比值恒为 `exp(-d²/SIGMA)`，与 `w` 无关。加权
只是让策略更在意这一项，从而部分抵消 `gait`/`pose`/`upright` 的静止偏好——它修的是第 2 个
问题，不是第 1 个。真正拉开区分度的只有 `SIGMA`：

| SIGMA | 0.1 m/s 下站着不动 | 0.3 m/s | 0.5 m/s |
|---|---|---|---|
| 0.25（我们改前） | **0.961** | 0.698 | 0.368 |
| **0.10（上游值，现在用这个）** | 0.905 | 0.407 | 0.082 |
| 0.05 | 0.819 | 0.165 | 0.007 |
| 0.02 | 0.607 | 0.011 | 0.000 |

### 顺带解释了一个之前单独发现的现象：低速死区

`tools/envelope.py` 测出 56 维和 61 维**在 +0.10 m/s 这个命令下都跟不动**（跟踪 0.46 / 0.93）。
当时记成"步态有最低速度死区"。看了上表第一列才明白：**在 0.1 m/s 的命令下，站着不动本身
就有 0.961 分**。策略不是走不了这么慢，是奖励告诉它"这个命令最正确的做法就是站着"。

这同时解释了为什么把 SIGMA 收到 0.05 也救不了低速：0.1 m/s 下站着仍有 0.819 分。**绝对宽度的
核在变速命令下必然产生低速死区**，要彻底解决得改成相对误差核（按 `|cmd|` 归一化），
否则低速段永远偏袒静止。上游用的就是绝对核，所以上游自己也有这个死区——只是它的核窄 2.5 倍，
死区比我们小。这和"真机摇杆必须留死区"的社区经验是同一件事，不是两个 bug。

而且上游用**另一个办法**把低速这段绕开了：`infer_policy.py` 的 `_update_policy_session()` 里

```python
new_policy = "standing" if magnitude <= 0.05 else "walking"
```

—— **命令幅值 ≤ 0.05 m/s 时切换到独立的 standing 策略**。"站着"在上游是另一个 ONNX 的职责，
不是一个策略内部的退化解。我们的 env 只有一个策略，所以它必须在两者之间自己选，而上面这张
表告诉它选"站着"是划算的。这是架构层面的差别，加多少权重都补不回来。

### 还有第四个静默 bug，而且它在奖励里：`gait` 权重 1.0 一直在送常数

`Duck.__init__` 里原来是这一行：

```python
self.foot = self.site[:, self.feet]     # self.feet 是 list
self.rot  = self.xmat[:, self.trunk]    # self.trunk 是 int —— 就在上面三行
```

看起来是同一件事，语义完全不同：

- `xmat[:, self.trunk]` 用**整数**索引 → basic indexing → **活的视图**，随物理更新
- `site[:, self.feet]` 用**列表**索引 → fancy indexing → **复制**

而 `site_xpos` 只由 `mj_forward` / `mj_step` 写入，`__init__` 跑在两者之前。所以 `self.foot`
在构造时就被复制成了**全 0**，之后再也不更新。

于是 `gait` 项（权重 **1.0**）里 `height` 恒等于 0。代进去看会发生什么：

```python
stance = exp(-(height/0.01)**2)          # height = 0  -> 恒等于 1
low    = min(height - SWING*phase, 0)    # 只剩 phase 项
high   = max(height - CEILING, 0)        # 恒等于 0
```

`gait = blend·swing + (1-blend)·stance` 变成一个**只依赖相位时钟和 `moving()` 的纯时间函数**。
它不能提供任何梯度，而且它**照样打印 0.83** —— 一个权重 1.0 的项，从第一天起就只是在给总
奖励加一个常数偏移，看起来却像一个健康的步态奖励。

同一个 `self.foot` 还被用在三处，一起中招：`BallBalance` 的 `feet_mid`（钉在原点）、以及本轮
新加的 `air_time`（本来会恒为 0，看起来像"策略从不抬脚"）。

**实测**：300 步、8 个环境、确定性策略，脚 site 的 z 在 p0–p100 **全部精确等于 0.00 mm**，
而同 id 的 `site_xpos` 读数是 0.011–0.013 m。改完立刻变成：

| 分位 | p0 | p50 | p90 | p99 | p100 |
|---|---:|---:|---:|---:|---:|
| 脚高 | −3.78 mm | **0.83 mm** | **9.29 mm** | 28.98 mm | 148.61 mm |

超过 8 mm 抬脚阈值的样本占 **12.5%** —— `robust61_a` 其实一直在抬脚，只是 `gait` 项根本没看见。

`foot` 现在是 property，每次访问重新读 `site_xpos`。`selfcheck.py` 加了三条断言 + 一个负对照
（把 property 换回全 0 的缓存，要求三条全红）。这套检查现在是 **23/23**。

⚠️ **`robust61_drmb` 及之前所有权重的 `gait` 都是常数**。不要跨这条界线比较奖励绝对值 ——
奖励尺度本身变了。策略的腿是真的在动，但那是 `track` 和 `pose` 驱动出来的，不是 `gait`。

### 怎么才能发现这种事

**不要看训练日志的 reward。** 上面两个例子 reward 都"几乎没变"。我们的做法是：

1. 训练日志里同时打印**实测速度**（`fall/1k` 也是同理，见下），而不是只看归一化的奖励项；
2. 每次训练后跑 `tools/envelope.py` 扫恒定命令下的真实 m/s ——**恒定命令**是关键，训练里的
   命令是每 3 秒重采样的，站着不动在重采样噪声下也能刷到不错的平均分；
3. 用 `tools/probe_robust_env.py` 把随机化逐项拆开，确认"是哪一项把策略打死的"。

`fall/1k` 这个指标也是同一次排查里加的：原来的 `falls` 是 `摔倒数/结束回合数`，训练早期
没有任何回合到达 1000 步上限，于是只要有一个机器人绊倒，比值就恒为 1.00，看起来像全线崩溃。
换成"每千环境的步数摔多少次"之后才有可比性。

## 健壮性：在自己的植物里测策略，等于什么都没测


评估一个策略时，最容易犯的错是**在它训练的那个物理环境里测它**。那只能说明它会做它唯一
做过的事。真机上有延迟、有噪声、有力矩上限、有地板差异，这些在训练里都不存在。

### 1. 物理基座先命名（`tools/plant.py`）

社区 `duckbench` 的 `PLANT.md` 记录过一次教训：两个同名 `scene.mjb` 大小相同、字节不同，
两边的数字被当成同一种测量比较了很久。这里把同一件事做在数字层面：

```bash
./.venv/Scripts/python.exe tools/plant.py
```

```
nominal          mass 0.7372 kg  force +-0.9600 N m  solver 100/50  ...
real_effort      mass 0.7372 kg  force +-0.6405 N m  solver 100/50  ...
solver_training  mass 0.7372 kg  force +-0.9600 N m  solver 10/20   ...
```

两个数字的来源要说清楚：`0.96` 是舵机堵转值，`0.6405 = kt × 1.75 A` 是驱动器电流限，
`10/20` 是 mjlab 训练用的求解器迭代次数（MuJoCo 默认 `100/50`，比训练硬 4 倍）。

### 2. 27 项条件压力测试（`tools/robustness.py`）

```bash
./.venv/Scripts/python.exe tools/robustness.py \
  --policy out/deploy61.pt --envs 8 --seconds 8 \
  --gates tools/gates.json --out out/robustness61.json
```

条件分两类：**换物理**（真实力矩 / 训练求解器 / 质量 +10% / 质心偏 1 cm / 摩擦 0.6 与 1.4 /
5° 斜面 / 10° 初始倾角）和**换控制环**（动作延迟 20–120 ms / 观测延迟 60 ms / 传感器噪声 /
0.3 m/s 侧向推挤），另加**换指令**（后退 0.25 m/s、纯转向 0.8 rad/s）。

三个指标口径刻意和社区一致（对齐 `HannesVonEssen/microduck-running` 的 eval JSON）：
跟踪率、最大倾角、航向误差、存活率、速度 p10/p90。

单 seed 是一个样本，不是一次测量。加 `--seeds 5` 会把每个条件跑 5 个种子：跟踪率取均值、
**摔倒取最差的种子**，并把 seed 间跨度单独打一列。8 envs × 8 s = 64 s 机器人时间，
`falls_max 0` 在这个样本量上本身就很宽——跨度那一列就是让你看结论有多少是运气：

```bash
./.venv/Scripts/python.exe tools/robustness.py \
  --policy out/robust61_a.pt --envs 8 --seconds 8 --seeds 5 --gates tools/gates.json
```

### 3. 门禁先写，再测（`tools/gates.json`）

门槛是**先登记**的：一份“上线就绪”该达到什么，写死之后跑测量，FAIL 是结论不是 bug。
这是 `duckbench` 的 `GATES.md` 做法——让后面的判断是查表，而不是争论。

### 4. 导出的图必须在闭环里跑过（`tools/deploy_sim.py`）

`export_onnx.py` 只证明**开环**数值一致。策略是反馈系统，1e-7 的差异可能长出另一条步态，
训练里没有的安全钳位也可能把吸引子挪走。所以这里用 ONNX 会话 + 延迟缓冲 + 安全层闭环跑：

```bash
./.venv/Scripts/python.exe tools/deploy_sim.py \
  --onnx out/deploy61.onnx --policy out/deploy61.pt \
  --conditions nominal,latency_60ms --safety
```

安全层做三件事：NaN 守卫、每拍速率限幅、关节行程 95% 钳位。**速率限幅必须先量再定**——
这个步态每拍动作变化中位 0.36 rad、p100 0.61，所以限到 0.25 等于每步改写策略（实测 2400
步里触发 2146 次），0.75 才是“只拦异常”。工具会把触发次数打出来，就是为了暴露这件事。

### 5. 不变量自检（`tools/selfcheck.py`）

```bash
./.venv/Scripts/python.exe tools/selfcheck.py --onnx out/deploy61.onnx
```

三件容易悄悄坏掉的事：关掉随机化后 `train_robust.Duck` 必须与 `train_official.Duck`
逐步完全一致（否则训练环境和出 checkpoint 的环境不是一个）、观测 61 维且重力块是单位向量、
导出的图输入名与宽度符合运行时契约。

另有两项是这一轮加的：`check_delay_advance()` 用「读回来的帧等于哪一帧」钉住观测历史的推进
次数；以及**负对照**——每次运行都故意改坏四处，要求对应检查必须变红。全绿但从不失败的自检
不算证据，详见 §「三个测量 bug」第 5 条。`--no-negative-control` 可以跳过。

### 6. 发布包（`tools/make_manifest.py`）

```bash
./.venv/Scripts/python.exe tools/make_manifest.py \
  --policy out/deploy61.onnx --robustness out/robustness61.json \

```

产出官方 schema 2 的 `manifest.json`（`obs_len` 从图里读，不手写）+ `policy.onnx` +
`media/preview.mp4`。清单里带 `status`、`deployment`（归一化是否烘进图、是否需要动作滤波）
和 `eval`（在什么植物上测的、过没过的门禁），这三是社区真机策略卡上最有用的部分。

### 已知缺口（写出来比藏起来好）

  没有这一层。这是目前最大的一处保真度缺口，只能标注不能假装。
- ~~**物理扰动是"整批共享"的**：mjbatch 一个 batch 共享一个编译模型，所以质量/摩擦/力矩

## 三个测量 bug，以及它们为什么能活这么久

这一轮没有再训新策略，而是回头问了一个更不舒服的问题：「我们凭什么相信之前那些数字？」
查出三处会**静默给出漂亮数字**的错，外加一处把能力缺口说成了物理限制的错误注释。全部已修，
并且加了能抓住它们的检查。

它们的共同点值得先说：**没有一处会报错。** 三处都让数字变好看，而不是变难看。

### 1. 动作延迟永远少一格，于是 `latency_20ms` 就是 `nominal`

发现方式不是读代码，是**看两个本该不同的条件给出了完全一样的数**：

```
condition           track    sd  falls   tilt    hdg
nominal             0.458  0.00   0/8     6.0     17
latency_20ms        0.458  0.00   0/8     6.0     17    <- 一行都不差
```

一个整控制周期（20 ms）的延迟不可能是免费的。原因在 `rollout()` 那行延迟线：

```python
deque([zeros] * act_delay, maxlen=act_delay)
```

往一个**已满**的 deque 里 append 会先挤掉最老的元素，`popleft()` 拿回来的就是**刚刚 append
进去的那个** action。`maxlen` 必须比延迟量多一格：`maxlen=act_delay + 1`。

影响：**此前所有 `latency_*` 条件的名字都比实际生效的延迟大 20 ms。** `latency_20ms` 一直在
测 0 ms（所以它和 `nominal` 一模一样），`latency_40ms` 测的是 20 ms，依此类推。

修完之后（`robust61_a.pt`，0.3 m/s，8 s × 8 envs × 3 seeds）：

| 条件 | 跟踪率 | seed 间跨度 | 摔倒 | 倾角 |
|---|---|---|---|---|
| nominal | 0.438 | 0.00 | 0/8 | 6.0° |
| latency_20ms | 0.396 | 0.00 | 0/8 | 7.3° |
| latency_40ms | 0.388 | 0.05 | 0/8 | 12.1° |
| latency_60ms | 0.245 | 0.10 | **29/8** | **47.1°** |
| latency_80ms | 0.503 | 0.07 | **56/8** | **47.9°** |

注意最后一行：**跟踪率 0.503 比 60 ms 那一格还高，而它摔了 56 次。** 这是「跟踪率不区分
走过去和滚过去」在数字上复发了一次。所以这张表必须先读摔倒/倾角，再读跟踪率。随之而来的
两条修正：

- `latency_20ms` 的 0.396 **低于**门禁的 0.65，这条门禁现在是 **FAIL**。它不是以前通过了，
  是以前根本没测过——被一个恒等于 `nominal` 的条件"通过"了；
- 结论从"60 ms 以内确实有救"改成"**40 ms 以内有救，60 ms 摔**"。这条恰好和训练时的
  `act_delay=(0,2)`（0–40 ms）自洽。之前那个结论和自己训练的范围是矛盾的，当时没看出来。

### 2. 观测历史在 `obs()` 里推进，于是有效延迟取决于别的机器人摔不摔

`train_robust.Duck` 用 `obs_hist` 实现观测延迟，而历史**每调用一次 `obs()` 就推一格**。
问题在于 `train_ppo.rollout` 在任何一个环境 reset 的那一步会调用 `obs()` **两次**（一次算
`next_obs`，一次在 `env.reset(ids)` 之后）。

于是：只要有别的机器人摔了，**整个 batch 里每个环境的历史都多推一格**，`d_obs=1` 悄悄变成
读两格前。这不是延迟模型，这是「延迟模型 + 一个按 batch 摔倒率触发的随机额外周期」。

修法是把推进从 `obs()` 移到 `step()`，`obs()` 变成纯读。`tools/selfcheck.py` 里新增的
`check_delay_advance()` 用「读回来的帧和哪一帧相等」来钉这件事，不看调用次数。

顺带修了同一处的第二个问题：reset 时 `obs_hist` 填了新数据，但 `act_hist`（动作延迟线）
没清，于是一个 `d_act=2` 的环境 reset 后会**重放上一段 episode 最后两个动作**——那是给躺在地
上的机器人算的。现在 reset 时清零，语义是"保持 home"，也就是策略刚加载时的状态。

### 3. 改了质量，但没告诉求解器

`tools/plant.py` 的 `mass_scale` / `payload_kg` 改完 `body_mass` 和 `body_inertia` 之后，只
手工重算了一个 `body_subtreemass`。不够。`mj_setConst` 同时重建 `body_invweight0`、
`dof_invweight0`、`actuator_acc0`，而**接触求解器用的是 `body_invweight0`**。

留下旧值的后果是：一个变重的机器人，被当成轻的来解约束。

| 质量 | `body_invweight0`（应为） | 实际留着 | 落地高度偏差 |
|---|---|---|---|
| 1.4× | 1.2632 | 1.7166 | 42 µm |
| 2.0× | 0.9181 | 1.7166 | 128 µm |
| 3.0× | 0.6434 | 1.7166 | 222 µm |

3× 时那个权重项错了 63%。所以 `mass_plus_*` / `payload_*` 这一批数字，都是在约束正则化偏硬的
植物里测的。绝对量不大（几百 µm），但它是**错的方向**，而且这正是 `plant.py` 自己在文档里
警告过的"写歪了不报错"的形状。

修法是换成 `mujoco.mj_setConst`。修完的强证据是：两条独立路径——本地改模型 vs
`Batch.expand` 逐仿真改——算出的轨迹**逐位相同**（高度差 0.0 µm，qpos 差 0.000000）。

### 4. 顺带推翻了 docstring 里一句"做不到"

`train_robust.py` 原来的原话是：

> What is deliberately *not* randomised: the plant itself (mass, friction, torque ceiling).
> mjbatch shares one compiled model across the batch, so those are chosen once by
> `tools/plant.py` and evaluated, not sampled.

**这句是错的。** 这个版本的 mjbatch 有 `Batch.expand(field)`：返回每个仿真的 `(N, ...)` 模型
字段值，每次物理调用前按行应用。`tools/probe_expand.py` 验了三件事：

1. `expand("body_mass") * 1.4` 之后，**派生**字段 `body_subtreemass` 的比值正好 `1.4000`；
2. 同一条轨迹和 `plant.build(mass_scale=1.4)` 逐位相同（这就是上一条的交叉验证）；
3. 一个 1.0 m/s 的侧向推：同 batch 里 `mu=1.0` 的行滑 0.139 m，`mu=0.1` 的行滑 0.377 m。

所以诚实的说法不是"不可能"，是"**没做**"。没做的代价是：`gates.json` 里每一条质量、负载、
摩擦门禁，测的都是策略从没见过的植物——它们只能被报成缺口，永远关不上。

现在有了 `--plant-dr`，按环境采样（默认 mass 0.95–1.10、摩擦 0.8–1.2、力矩上限 0.6405–0.96）。
`body_mass` 改动需要 `set_const`，实测 64 个仿真 0.49 ms，相对一次 2048 env 的 step 可以接受。

### 5. 两个让"数"变成"量"的工具改动

**`robustness.py --seeds N`。** 默认一直是单 seed。8 envs × 8 s = 64 s 机器人时间，`falls_max 0`
这种门禁在这个样本量上置信区间宽到没有意义：64 s 里摔 3 次和摔 0 次，不足以分开"可靠"和"运气"。
现在 `--seeds > 1` 时跟踪率取均值、**摔倒取最差的那个 seed**（摔一次就是摔过），seed 间跨度
也打出来，让读者自己看结论有多少是种子决定的。

**`selfcheck.py` 的负对照。** 之前 15 项检查全绿，但"全绿"本身不是证据：一个什么都不检查的
断言、或者拿代码自己算出来的错值去比对的断言，也会一样响亮地绿。所以现在每次都故意改坏四
处，要求对应的检查必须变红：

| 故意改坏 | 应当抓住它的检查 |
|---|---|
| 动作通道乘 0.1% | `robust env == official env` |
| `plant.build` 忽略 `mass_scale` | `perturbations are independent` |
| 去掉质量编辑后的 `mj_setConst` | `cached solver constants` |
| 延迟历史改回在 `obs()` 里推进 | `d_obs=1 reads the pre-step frame` |

四条全部被抓住（26/26）。第四、三条正是上面第 1、3 个 bug 的回归钉子。

## 延迟到底是多少：一次更正，以及更正的方法

这份文档早先写过「`delay_min_lag=3, delay_max_lag=6`，也就是 60–120 ms」。**这个数字是错的**，
错在把 lag 当成了控制周期。查 mjlab 源码文档才看到原话：

> Delays are quantized to physics timesteps (not control timesteps). For example, with 500Hz
> physics and 50Hz control (decimation=10), a lag of 2 represents a 4ms delay (2 physics steps).

（`mjlab.actuator.DelayedActuatorCfg`，https://mujocolab.github.io/mjlab/v1.1.1/source/api/actuator.html）

microduck 训练用的是 500 Hz 物理，所以 **6–12 ms**，不是 60–120 ms。`DelayBuffer` 按物理步
索引这个事实和 `DelayBuffer(min_lag=..., update_period=...)` 的注释也是一致的。

有一个独立的旁证：如果真机真有 60–120 ms 的动作延迟，上游的策略在真机上根本走不起来。
而我们的测量是 40 ms 跟踪率就掉到 0.46、60 ms 直接 26 次摔倒。上游机器人是能走的，所以
6–12 ms 才是自洽的那个解。**当文档和实测打架时，先怀疑自己读错了单位。**

> ⚠️ 上面这句里的「40 ms / 60 ms」是被上面的延迟 off-by-one bug 污染过的数字：当时标 40 ms
> 的条件实际跑的是 20 ms，标 60 ms 的实际是 40 ms。**结论不变**（延迟确实远小于 60–120 ms），
> 但具体是「20 ms 就掉到 0.46」——比原来更严重，也就更支持 6–12 ms 这个读法。

同一次核对还发现两件事：

1. **观测延迟是逐项设置的，不是全局一个数。** `microduck_velocity_env_cfg.py` 里 gyro 和
   gravity 是 0–1 个控制周期（2026-07 的一次审计把它从 3 降下来了），而 `joint_vel` 是**恒定
   1 个周期**——因为 Dynamixel 固件就是用位置差分算速度的，这不是随机化，是传感器路径的物理
   属性。我们的 `train_robust.py` 一开始因此把 `jvel_lag` 做成**无条件开启**，结果训练出的策略
   反过来依赖这个滞后：`nominal`（无滞后）0.438 而 `obs_lag_official` 0.801，把滞后关掉反而
   半速。这是无偿的可移植性风险（别人自己编译 `duck-control`、或固件报真速度时就退化），
   所以最终改成**概率 0.5 的逐环境采样**，两种世界都见过。
2. **`DelayedActuatorCfg` 在 mjlab v1.1.1 里已经删了。** 延迟改成直接写在任意 `ActuatorCfg`
   子类上（`delay_min_lag` / `delay_max_lag` 成为基类字段），`delay_target` 也没了，自动作用
   在 actuator 自己的 `command_field` 上。照老名字去搜会找不到。

### 为什么这件事值得单开一节

因为我们差点把一个 10 倍的量级错误当成「上游训练得不够健壮」写进结论。测量工具
（`tools/robustness.py` 的 `latency_*` 扫描）本身没问题，是**读参数的人**给了它错误的输入。
所以现在所有随机化范围都在代码里标了出处文件名，而不是凭印象：

| 量 | 值 | 出处 |
|---|---|---|
| 动作延迟 | 6–12 ms（3–6 物理步 @500 Hz） | `DelayedActuatorCfg` 文档 |
| 质量 ±5%、质心 ±3→±8 mm 课程 | | `microduck_velocity_env_cfg.py` |
| 足底摩擦 0.7–1.3 | | 同上 |
| 推挤 ±0.3 m/s，每 3–6 s | | 同上（`VELOCITY_PUSH_RANGE` / `_INTERVAL_S`） |
| 编码器偏置 ±0.015 rad | | 同上 |
| kp/kd 随机化 | **关闭**（`ENABLE_KP_RANDOMIZATION=False`） | 同上 |
| 倾角 pitch 10° / roll 5° | 定义了但**未启用** | 同上 |
| 安全层钳位 | ±π，是**执行器行程**不是单关节解剖限位 | `duck-control/src/safety.rs` |
| 速率限幅 | **没有** | 同上 |
| 死手开关 | 500 ms | 同上 |

最后两行值得单独说：`safety.rs` 里 `ACTUATOR_MIN/MAX` 是 ±π，那是舵机的行程，不是每个关节
自己的解剖学限位——因为 MJCF 里的 joint limit 没有被 vendor 进来。所以「安全层会保护关节」
这个说法在真机上是**不成立**的，它只防 NaN 和超出舵机行程。`deploy_sim.py` 的 `SafetyLayer`
按同一语义实现，默认速率限幅也是关的，就是为了不引入一个上游没有的保护层，从而测出一个
上游不存在的鲁棒性。

## 把延迟训进去：三个负结果

`train_robust.py` 的思路是把动作延迟、观测延迟、噪声、推挤放进训练循环，让策略在它要跑的
环路里学。这条路我们走了三次，三次都有可复现的结论，但**没有一次得到可以宣称"更好"的权重**。
写在这里是因为失败的诊断比成功的数字更有用。

### 负结果 1：学习率。热启动不是接着训

第一次直接 `--init deploy61.pt` 用默认 `LR=1e-3`、5 个 epoch。奖励 16 轮内从 3.71 掉到 **-0.35**，
`falls` 立刻恒为 1.00。原因是 PPO 的默认超参是给"从零学走"调的，每次 rollout 走 20 遍全批
梯度；对一个已经会走的策略，这个步长会把它直接踢出可行域。

修正：热启动时 `LR` 降到 2.5e-4、epoch 降到 3。同一套随机化下奖励稳定在 3.83。

### 负结果 2：奖励分不清"站着"和"走"

用修好的学习率跑完阶段 A、再加观测延迟和关节速度随机化跑阶段 B，奖励只从 3.84 掉到 3.71，
看起来"只是变难了一点"。实测：恒定 0.3 m/s 下速度从 **0.127 m/s 掉到 0.085 m/s**，其中
"干净条件"下从 0.136 掉到 **0.005 m/s**——策略学会了站着不动。

原因在 `track = exp(-|v-cmd|²/0.25)`：站着不动在这个命令下就有 0.698 分，而 `gait`/`upright`/
`pose`/`height` 四项全都在奖励静止姿态。把 `track` 权重乘 3 重跑（`--track-weight 3`），
"干净条件"恢复到 0.132 m/s，但**仍然没超过阶段 A**，所以这一步只是止损，不是改进。

#### 更深一层：那四项正则里有三个是写错的（2026-10-23 补）

上面那段解释只对了一半。上面说"`pose`/`upright` 在奖励静止姿态"——它们的**方向**没错，
但它们其实**什么都没约束**。把上游的实现从 `microduck/tasks/mdp.py` 逐行读出来对比：

| 项 | 上游实现 | 我们的实现 | 10° 倾斜 / 0.1 rad 误差下的得分 |
|---|---|---|---|
| `pose` | `exp(-**mean**(err²/**std²**))`，std 按关节 0.05–0.4 | `exp(-**sum**(err²))` | 上游 **0.64**，我们 **0.9** |
| `upright` | `exp(-tilt_sq/0.05)`，`tilt_sq = 1−cos(tilt)` | `exp(-2·sin²(tilt))` | 上游 **0.738**，我们 **0.941** |

`pose` 差在"少了个分母"：std 最紧的是 `hip_roll` 的 **0.05 rad**，也就是
(0.05/0.05)² = 1 个 e-fold；我们那版里同样的误差只值 0.0025。

`upright` 差在指数小了 5 倍（0.06 对 0.30）。它不像 `pose` 那样完全失效——0.941 和 0.738
还是有区分度——但**方向是"越歪越不算事"**，而走路本身就是一系列可控的倾倒。

**这里有个陷阱，我第一版就掉进去了。** 我们的误差量是 `sin²(tilt)`，上游是
`1−cos(tilt)`，两者**差整整 2 倍**（10° 时 0.0302 对 0.0152）。只补 `/0.05` 而不管这个 2，
结果是**比上游严格 4 倍**：10° 给 0.299，而正确的是 0.738。实测后果是 `robust61_u1`
的跟踪率掉到 8%、`air_time` 掉到 0.02——**比改之前更保守**，因为"每歪 10° 就重罚"的策略
只能选择站着。正确写法是 `exp(-0.5·sin²(tilt)/0.05)`。

这件事的方法论教训比 bug 本身重要：**我当时写的自检是"10° 必须 < 0.35"，而它确实变严了，
所以通过了**。断言"朝正确方向变化"抓不到过度修正。现在改成断言**与上游公式数值等价**
（误差 < 2%），它会在 0.299 vs 0.738 时立刻红。


第三处是权重本身，全线偏小：

| | 上游 | 我们（旧） | 倍数 |
|---|---|---|---|
| `track` | 2.0 | 1.0 | 0.5× |
| `turn` | 2.0 | 0.5 | **0.25×** |
| `pose` | 1.0 | 0.5 | 0.5× |
| `upright` | 2.0 | 1.0 | 0.5× |

合计正项 4.5、负项 −1.605，比值 **2.8**；上游是 10.0 对 −1.27，比值 **7.9**。
**我们的惩罚相对重了 2.8 倍**，加上两项正则形同虚设，"少动"自然是优解。

现在 `--upstream-rewards` 一次把整套换掉：权重照抄，`pose` 换成逐关节 std 的
`mean` 版，`upright` 补上 `/0.05`，**上游没有的项一律清零**（`gait`/`height`/`slab`/
`torque`/`limits`）。其中 `gait` 清零代价最大——它是那个 667 ms 参考时钟，权重 1.0，
去掉之后步态形状只能从 `air_time` 里涌现，而 `air_time` 是每步 0/1/2 的稀疏信号。

顺带一个数字：`turn` 现在是权重 2.0 × 核 0.50。yaw 误差 1.0 rad/s 时得 `0.135×2.0 = 0.27`，
而最初是 `0.018×0.5 = 0.009`。**转向信号强了约 30 倍**。这是第一次，如果策略还是不会转，
就不能再赖奖励了。

### 负结果 3：微调是能力置换，不是帕累托改进

这一节原来的表格把 `deploy61` 写成"后退/转向/侧移都占优"，**那个解读是错的**。加上倾角一列
（`tools/ab_compare.py`，12 环境 × 10 秒）就看出来了：

| 命令（真实传感器模型） | deploy61 跟踪率 | deploy61 倾角 | robust61_a 跟踪率 | A 倾角 |
|---|---|---|---|---|
| 前进 0.30 m/s | +0.16 | **45.1°** | +0.39 | 6.4° |
| 前进 0.50 m/s | −0.03 | **46.3°** | −0.11 | 12.4° |
| 后退 −0.25 m/s | +1.19 | **19.5°** | +0.53 | 5.6° |
| 转向 0.8 rad/s | +1.63 | **45.8°** | +0.78 | 5.1° |
| 侧移 0.15 m/s | +0.98 | **45.7°** | +0.75 | 5.3° |
| 慢速 0.10 m/s | −0.21 | **46.0°** | +0.81 | 5.6° |

`deploy61` 在真实传感器路径下的倾角**几乎每一格都在 45° 左右**——它不是走得比阶段 A 好，
它是**一直躺在地上**，而"躺倒过程中翻转产生的位移"被计成了跟踪率。转向 1.63 看起来比命令
还多，正是因为它在地上打滚。同一次运行里它摔了 15 次，这个数字当时也在表里，只是被
"跟踪率高"这个结论盖过去了。

**所以 `deploy61` 在真实部署条件下完全不可用，而阶段 A 是唯一站得住的候选。** 这不是能力置换，
是基线根本不能用。之前的结论修正如下：

- 阶段 A 的真问题不是"置换"，是**后退弱**（0.53，且有方向反的风险）和**前进只有 0.39**；
- 它换来了延迟容忍（`latency_*` 全部 0 摔倒直到 60 ms），这是真的——**但「直到 60 ms」这个
  数字要按 §「三个测量 bug」第 1 条重读**：修掉 off-by-one 之后，`robust61_a` 在 40 ms 仍
  0 摔倒、0.388 跟踪率，60 ms 摔 29 次、倾角 47°；
- 所以结论是"**这个小机器人在 40 ms 以内确实有救，60 ms 摔**"。和训练时的 `act_delay=(0,2)`
  完全一致——之前写的"80 ms 才崩"是错的，那个条件实际跑的是 60 ms，而且摔了 56 次。

### 一个测量陷阱：高跟踪率可能是翻倒

上面这个错误值得单独记下来，因为它是最容易骗到人的一种：

**跟踪率是沿命令方向的净位移，它不区分"走过去"和"滚过去"。** 一个翻倒中的机器人四肢乱蹬、
躯干翻转，很容易在 10 秒里产生比正常步态更大的净位移。所以

> 任何"速度/跟踪率"指标，必须和倾角、摔倒数**同时**读。

`tools/ab_compare.py` 因此改成同屏输出三张表（跟踪率 / 摔倒 / 倾角），并且在倾角表的脚注里
写明"高跟踪率 + 高倾角 = 在摔，不是在走"。那次是 15 次摔倒这个数字就在同一份输出里，
只是我先看了跟踪率、没看它。

之后又发现一个更隐蔽的同类问题：`envelope.py` 早先 6 秒的结果"好看"、12 秒全崩，原因也是
状态污染（命令点之间不 reset），同样属于"指标的读数被非目标因素污染"。

### 负结果 4：三根旋钮都试过了，没有一根能超过阶段 A

针对"奖励分不清站着和走"，先后试过三种改法。前两种失败，第三种在数学上是正确解、
也确实大幅提升了无滞后条件下的速度，**但在真实传感器路径下反而更差**：

| 改法 | 做法 | 结果 |
|---|---|---|
| ① 加权 | `--track-weight 3` | 0.004 → 0.132 m/s，止损但超不过阶段 A |
| ② 收窄核 | `--sigma 0.05` + 加权 ×3 | 后退修好了（0.53→0.77），**转向归零**（0.78→−0.03） |
| ③ 基线归一化 | `--track-baseline` | clean 下 0.42→0.85，**official 下反而从 0.39 掉到 0.05** |

**① 为什么不行**：`w · exp(-d²/σ)` 里的 `w` 在指数外面，所以"站着 / 走对"的比值恒为
`exp(-d²/σ)`，跟 `w` 无关。加权只改变了这一项相对 `gait`/`pose`/`upright` 的分量，
碰不到比值本身。

**② 为什么不行，而且这里我犯了个实验设计错误**：`--track-weight` 只乘 `track`，
**没有乘 `turn`**。这两个是同类的任务奖励（线速度跟踪、角速度跟踪），一个放大 3 倍一个不动，
等于把转向的相对权重压到 1/3。日志能直接看到：

| 轮次 | track 项 | turn 项 | turn/track |
|---|---|---|---|
| 阶段 A（无加权） | 0.87 | **0.24** | 0.276 |
| v2（w=3） | 2.67 | 0.19 | 0.071 |
| S（w=3 + σ0.05） | 2.16 | **0.08** | 0.037 |

turn 从 0.24 掉到 0.08，正好对应转向能力从 0.78 掉到 −0.03。**所以 S 这一轮不能用来判定
"收窄 σ 有没有用"，它同时改了两个变量。** 这个错误的教训比结果本身值钱：
**凡是"加权"，先问清楚它乘了哪些项、没乘哪些项。**

**③ 数学上正确的做法：减基线再归一化**

问题不在核的宽度，在于这个核度量的是"接近程度"而不是"跟踪"。站着不动确实离命令很近。
正确的改法是把"站着不动"这个参照点减掉：

```
t' = (exp(-d²/σ) - exp(-|c|²/σ)) / (1 - exp(-|c|²/σ))
```

- 站着不动（d = |c|）恒为 **0**
- 走对（d = 0）恒为 **1**
- 与 σ 无关、与命令大小无关

这样 σ 才回到它该有的含义：**只控制中间误差扣多狠**，不再兼职"区分度"。而且它顺手解决了
低速死区——0.1 m/s 下站着不动也是 0 分，不再是 0.961。`turn` 用 `|cmd_yaw|` 作基线同样处理。

两处必须的保护（都是先踩了才加的）：

| 保护 | 不加会发生什么 |
|---|---|
| 零命令时**掩掉**该项，而不是给分母一个下限 | `cmd_yaw = 0` 时分母 `1-exp(0) = 0`，钳到 `1e-3` 后，偏航速度噪声 0.3 rad/s 被放大成 **turn −287**，训练第一轮就崩 |
| 结果裁剪到 `[-1, 1]` | 0.1 m/s 命令下分母只有 0.039，走反会得到 **−15** 并被 `FLOOR` 截断。走反 2 倍和走反 10 倍都是"完全错"，不该差 15 倍；无界惩罚还会让策略宁愿站着（0）也不愿尝试（±1） |

归一化在数学上是对的（`out/robust61_n.pt` 的 `track` 从 A 的 0.34 升到 0.46，clean 下 0.3 m/s
的速度从 0.125 翻到 0.256 m/s），但它**没有赢过阶段 A**，而且输得很有规律：

| 真实传感器模型 | deploy61 | **robust61_a** | robust61_s | robust61_n |
|---|---|---|---|---|
| 前进 0.30 | 0.16（倾角 45°） | **0.39**（6.4°） | 0.24 | 0.05（14.8°） |
| 前进 0.50 | −0.03（46°） | −0.11 | +0.02 | 0.23（**46°、11 摔**） |
| 后退 −0.25 | 1.19（假） | **0.53** | 0.77 | 0.13 |
| 转向 0.80 | 1.63（假） | **0.78** | −0.03 | 0.25 |
| 侧移 0.15 | 0.98（假） | **0.75** | 0.57 | 0.52 |
| 慢速 0.10 | −0.21 | **0.81** | 0.70 | 0.50 |

### 为什么归一化反而在真实条件下更差：一个控制论解释

对比同一份权重的两个传感器模型，落差本身就是答案：

| | clean（无滞后） | official（真实路径） | 落差 |
|---|---|---|---|
| robust61_a | 0.42 | 0.39 | **1.1 倍** |
| robust61_n | **0.85** | 0.05 | **17 倍** |

归一化把"走对"的奖励梯度变陡了（分母 `1-exp(-|c|²/σ)` 在 0.3 m/s 时只有 0.30），策略因此被逼
出**高增益**的行为：在无滞后的世界里能精确跟到 0.85。但**高增益控制器对延迟敏感是控制论的
必然**，不是训练没收敛——`robust61_n` 在 official 下前进 0.3 的倾角从 clean 的 4.8° 涨到 14.8°
（振荡的指纹），0.5 m/s 直接 46°、摔 11 次。它在来回修正一个永远晚一拍的状态。

阶段 A 走的是另一条路：精度要求低（宽核、不归一化），于是学到了**低增益的慢走**，
0.118 m/s 换来 6.4° 的稳定倾角。所以：

> **阶段 A 的"慢"不是缺陷，是它换取延迟下稳定性的代价。**
> 「走得准」和「延迟下走得稳」在这个植物上互斥，奖励的精度要求决定策略落在哪一边。

这也解释了为什么阶段 A 在 `slow .10` 这一格最好（0.81）——它本来就是按"慢而稳"调出来的。

**所以这条路的上限就是阶段 A。** 三种奖励改法（加权、收窄核、基线归一化）全部试过，
方向各不相同，没有一种能超过它——因为瓶颈不在奖励的形状，在于"在有延迟的观测下精确跟踪"
本身需要更多训练量或延迟课程，而不是一个更好的核。归一化那一版留给**从零训练**的场景：
它把一个模糊的奖励变成了可解释的量，这个价值独立于本次结果。

### 这件事对门禁意味着什么

阶段 A 在 27 项门禁里过 2 项（`obs_lag_official` 0.801、`cmd_yaw` 0.464），**唯一过的那个恰好
是真实部署条件**，而 `nominal`（无任何延迟）FAIL 到 0.438。

这不是自相矛盾，是门禁套件本身的结构问题：`nominal` 这个"合成干净条件"对一个为真实环路训练
的策略来说是分布外。所以一个策略可以在部署条件下最好、却在门禁表上几乎全红。要判断"能不能上
机"，得看部署条件那一行，不能数 PASS 个数。这条写在这里，是为了以后不要再拿 PASS 数量当结论。

## 四个 plant-DR 变体全是负结果，但根因不在 DR

`--plant-dr` 是这一轮新加的能力（逐仿真环境改物理）。它的四个变体没有一个变好：

| 权重 | `--plant-dr` | dt | 训练 `track` | 评估 `tracking_ratio` | 读作 |
|---|---|---|---:|---:|---|
| `robust61_a` | 无（对照） | 0.005 | 0.87 | **0.438** | 真的在走 |
| `robust61_dr` | 全轴 `0.95,1.05` | 0.002 | — | 不作数 | 配置有 bug，见下 |
| `robust61_dr5` | 全轴 `0.95,1.05` | 0.005 | 0.81 | 0.297 | 退化 |
| `robust61_drm` | **只质量** `0.95,1.05` | 0.005 | 0.79 | **0.002** | 冻结站立 |

`robust61_drm` 是彻底的死策略：`nominal` 跟踪率 0.002，倾角 1.3°，8 个环境零摔倒——
它不是"走得差"，是**根本没在走**。

### 真正的问题：训练曲线上的 `track` 测不出这件事

三个权重真实跟踪率差 **200 倍**，而训练日志里的 `track` 只从 0.87 变到 0.79。
原因还是第一节那个算式：`track = exp(-|v-cmd|²/0.25)`，站着不动对 0.3 m/s 的命令
得 `exp(-0.09/0.25) = 0.698`。**0.79 就是"站着"的分数，0.87 是"在走"的分数，
中间的 0.08 才是全部动态范围。**

所以这批实验的失败是**两条独立问题叠在一起**：

1. 训练指标没有分辨力 —— 就算 DR 真的有用，这个数字也显示不出来；
2. `robust61_dr` 那次还叠加了配置错（`--plant-dr "0.95,1.05::"` 当时会把未写的轴
   补回默认值，于是"只开质量"实际上开了三轴；同时误用了 `--timestep 0.002`）。

修复是**先把尺子的刻度做出来**，而不是继续调旋钮。`train_ppo.rollout` 现在把
实际对地速度按命令方向投影，直接打进进度条：

```
...  fall/1k 0.24  v +0.412/0.30
```

`v` 的定义与评估里的 `tracking_ratio` 完全一致（沿命令方向的带符号速度 / 命令模长），
所以两者可以直接对读。随机初始策略打出来是 `v -0.000/0.24`，站着不动一眼可见。

上游 `AGENTS.md` 里有一句同源的话：

> Watch per-iteration: ... **the MAIN task term actually growing (total reward can rise
> purely on regularizers while the trick never happens).**

`robust61_drm` 的总奖励 3.62 全程正常，`pose` 甚至从 0.72 涨到 0.86——涨的正是"保持站姿"。
总奖励和正则项都在变好，主任务项在变坏，这就是那句话的实例。

### 一个顺带测到的代价：plant-DR 让训练慢 3 倍

`drm` 是 30k steps/s，`drmb`（同样配置 + `--track-baseline`）只有 19–20k。两者 `fall/1k`
分别是 0.2 和 18–20。摔倒多 → `reset` 多 → 每次 `reset` 都要 `_draw_plant` →
`set_const(ids)` 重建求解器常量。**这是 plant-DR 的固有开销，不是实现的 bug**，
但选它的时候要知道：早期策略越差，这个开销越大。

### 直行偏航大概率不是我们的 bug

`zhuoligetu123/microduck-hd1910m` 用**上游四个官方 ONNX**（不重训）在**完全适配的 HD1910
硬件**上跑，自述的第一条缺陷就是"**仍有直行偏航**"。它同时也说翻滚"其他倒地初态未全部通过，
不能据此宣称实机验收"。

这条的价值是校准期望：**这台 25 cm / 737 g 的小机器直行会飘，是硬件+舵机特性的固有结果，
不是训练没做好。** 也解释了上游为什么专门做 `heading_hold` 课程（先走直线再学转向）和
`heading_tracking`（`ang_vel_z` 从 ±1.0 收到 ±0.5 才压得住"转向太猛"）。真机上摇杆必须留
死区，也是同一件事。

另外它把 50 Hz 时序列为**必须逐项核对**的项之一，环境名里带 `Slew`（限斜率）—— 说明 HD1910
的指令变化率要在**环境层**限制，不是靠后处理平滑。这对我们后面接真机是一条直接的提醒。

## 国内这条路已经有人走完了：XGO-Duck

陆吾智能（Luwu Dynamics）把 Microduck 适配成了完整可复刻的产品，硬件路径和本目录此前的
推演**几乎完全不同**：

| | 本目录此前的方案 | XGO-Duck |
|---|---|---|
| 舵机 | Dynamixel XL330，¥238–255，超压到 8 V 跑 | Feetech HD-1910-C001，15 颗，**4–8.4 V 额定**，8.4 V 下堵转 1.47 N·m |
| IMU | LSM6DSV16X + 自研 `imu_to_dxl` 板 | QMI8658A，融合跑在 Linux 侧 |
| 主控 | Radxa Zero 3W | Arduino UNO Q（Qualcomm Linux 50 Hz + STM32U585 100 Hz 双脑） |
| 齿隙 | 「最大保真度缺口，只能标注」 | 有实现 |
| 起身 | 没做 | 独立 get-up 策略 + 倾角状态机 |

其中对我们最重要的三条：

1. **`xgoduck_runtime_arduino` 的 61 维观测和我们的逐行一致**（`rl_core.build_obs` 里
   `obs[55:61] = 0.0` 写死），等于独立实现了同一份契约，验证了我们从 MJCF 推出来的布局；
2. **双脑架构**：MCU 100 Hz 发状态快照，Linux 50 Hz 读最新、**过期周期直接跳过不排队**——
   这比"提高 Linux 定时精度"更根本，也解释了为什么 50 Hz 策略不需要 100 Hz 定时器；
3. **动作低通 α=0.45 我们抄了但没用**——不过**这个"没用"的结论是错的，得收回**。
   实测：40 ms 延迟上跟踪率从 0.383 掉到 0.278，60 ms 上摔倒从 28 涨到 40。
   我们当时把它记成"低通对延迟没帮助"，但上游 `AGENTS.md` 的
   *Sim2real footguns* 一节写着：

   > **Policies are UNFILTERED** (no action low-pass in training). Don't add EMA
   > filtering without a matched runtime flag and a transfer test —
   > trained-with / deployed-without (either direction) breaks transfer.

   我们的做法恰好是后者：**给一个没带滤波训练出来的策略，在评估时加滤波**。
   所以那组数字测的是 train/deploy 不匹配，不是低通本身。要么两侧都加（重训），
   要么两侧都不加。**在评估脚本里加滤波这个行为本身，就是在制造我们要测的那种失效。**
   见 `tools/robustness.py` 的 `lpf_leg45`，现在它只作为"不匹配有多贵"的证据保留。

细节、代码位置、以及哪些能搬哪些不能搬（**硬件仓库没有 LICENSE 文件**，个人复刻可以、
商用需授权）见项目根的 `microduck-XGO-Duck对照.md`。

## 仿真模型和真机对不对得上：四个数字

所有关于"重心在哪、支撑域多大、头有多重"的判断，都建立在 `repo/microduck/robot_walk.xml`
就是真机这一点上。此前这只是假设。这一轮拿到了国内复刻者的实测记录
（`chenkui164/microduck-replica` 的 `调试记录.md`），可以直接对：

| 量 | 真机记录 | 我们的模型（MuJoCo 直接算） | |
|---|---|---|---|
| 整机质量 | 744 g | **737.2 g** | 差 6.8 g = ToF + 摄像头 + 螺丝 |
| 颈+头子树质量占比 | "头占三分之一"；上游 `AGENTS.md` 写 38% | **38.0%**（279.9 / 737.2 g） | 精确命中 |
| 大腿长 | 42 mm | **42.2 mm** | — |
| 小腿长 | 49 mm | **49.4 mm** | — |

关节限位也逐项一致：髋 yaw 左 −25/+30°、右 −30/+25°（镜像），hip_roll ±22°，
hip_pitch / knee / ankle 各 ±90°，neck_pitch −90/+60°，head_pitch ±90°，head_yaw ±170°，
head_roll ±25°。

**所以仿真里量出来的重心、支撑域、质量占比可以直接用来判断真机行为**，这也是"头占 38% 会让
头部跟踪的 std 收太紧就站死"这条结论能成立的前提 —— 头一动，质心是真的会大幅移动。

顺带三条装机时才用得上、但现在就该记下的硬件事实：

- HD-1910 是 **4096 步 / 360°**，`1° ≈ 11.4 步`，零点 2048 = MJCF 全 0 = 笔直站立。
  **站姿不是零点**：官方 `DEFAULT_POSITION` 是髋 pitch ±26°、踝 ∓26°、颈/头 pitch +20°，
  那是软件偏移，别把站姿校成 2048。
- **HD-1910 的位置计数方向跟 XL330 相反，15 颗全反**，运行时方向全部取 −1。这是"仿真里走得
  好好的、真机往反方向动"最可能的来源，而且它与策略无关 —— 取反不改变观测/动作语义，
  所以不需要重训。
- 出厂**过流保护、过压保护都是关的**，装机后堵转是常事，不开就是烧舵机。电池满电 8.4 V 正好
  等于 HD-1910 的电压上限（零余量），带载压降到 6.6–8.2 V 才回到安全区 —— 上游那个
  `vin_range=(6.5, 8.2)` 就是照这块电池定的，不是随手写的。

## 性能实测

| 项目 | 作者（8 vCPU） | 本机（20 核） | `microduck-lab`（M 系 Mac） |
|---|---|---|---|
| 训练吞吐 | 16k env-steps/s | **50–56k**（短测）/ 28k（长跑稳态） | 16.5k（32 env 配方）/ 27k 峰值 |
| 1500 次迭代 | 2 h 36 min | 约 50–86 min | — |

GPU 全程未使用。这不是省钱，是这套流水线的物理代价本来就在 CPU 上。

`jonathanhawkins/microduck-lab` 的 README 报 32 环境配方下 **~16.5k env-steps/s**（约 1 分钟
100 万步），吞吐配置下峰值 27k。所以我们的 30k 是它的 **1.8 倍**。注意它的配方是 **32 环境**、
我们是 2048 —— 单看 steps/s 不算完全公平，但结论是清楚的：**一台普通 Mac 就能在几分钟内训出
一条会走的策略**，说明瓶颈不在算力。这与前面"根因在奖励核和缺失的 `air_time`"的结论一致。

同一份 README 也自己划了界线：lab 是 **99 维**观测的**原型**契约（"not a sim2real one"），
要上真机必须回上游用 GPU 重训。能借的只有工程手段，布局不用照搬。
