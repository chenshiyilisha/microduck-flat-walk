## Microduck 技术深挖（第二轮，读源码）

产出 `microduck-技术深挖.md`。看了 constants / velocity_env_cfg / friction_dr_bam / backlash / testbench / pyproject。

关键参数（可直接引用）：
- BAM M6 执行器：kp_fw=200、vin 6.5–8.2V、vin_drop_gain 0–0.2、vin_min 6.0、delay 3–6 拍（50Hz ⇒ 60–120ms）。
- 摩擦 DR 不能走 dr.dof_frictionloss（BAM 下被清零，是静默 no-op），必须乘 BAM 的 friction_scale。
- 齿隙：每关节 passive_<joint>_backlash ±1°，编码器读 qpos[main]+qpos[backlash]，cmd.vel 故意留电机侧。
- PPO：512-256-128 ELU、lr 1e-3 adaptive(kl=0.01)、24 步/env、5 万迭代、4096 envs。
- 指令：lin_x ±0.4 / lin_y ±0.3 / ang_z ±1.0，固定不做课程；15% env 强制原地转。
- 地形：台阶 ≤1.5cm、坡度 1.7–5.7°；地形 geom solref 0.02→0.04 防 NaN。
- `xl330_test_bench` 是单舵机 sim/real A/B 台架，复刻党最该抄的东西。

核心判断（报告第 10、11 节）：工具链/方法论 100% 可移植，参数一行不能抄；飞特路线必须重辨识执行器 + 重训，无 CUDA 则不可行。

## Microduck 第三层：奖励工程与评测

产出 `microduck-奖励与评测.md`。读了 mdp.py（7188 行 / 230 函数）+ microduck-arena + microduck-challenges。

关键发现：
- mdp.py 顶部有 4 个 monkey patch：RewardManager.compute NaN 清洗、PPO.compute_returns 优势清洗、exporter 过滤 passive 关节（第 3 个 std clamp 在 mjlab 1.3.0 迁移时删除）。
- 三个被刷爆的奖励：躺着抖腿刷 air_time（→ 40° 倾角掩码）、坐着/躺平/头当三脚架刷状态奖励（→ potential-based shaping Δcos(tilt)）、头部紧容差导致放弃迈步（→ 宽高斯 + EMA-L1 拆开计价）。
- 头部占整机质量 38%；紧容差实测 0.77/step vs air_time 1.01/step，wandb run 5yay13u4（2026-08-20）。
- air_time_adaptive：走路摆动 100–250ms、奔跑 50–250ms，阈值 0.5 m/s。
- Arena：一条参赛 = 33 次仿真（5 seeds × 速度扫频），部署时重测 golden run，不复现就构建失败；成绩永远重测不读回；本地成绩官方明示不可比（舵机模型混沌）。
- 挑战赛把 reward 调参做成三旋钮竞技：forward/upright/step，4096 envs、3000 迭代。

可迁移结论（已写进报告第 9 节）：奖励分「逃不掉/能逃掉」两类计价；只奖进展不奖状态；每个行为奖励都问「错误状态下是否仍成立」并掩码掉。

## Microduck 第四层：控制环 + 情感设计

产出 `microduck-控制环与情感.md`。读了 policy.rs(816行)、safety.rs(937行)、emotions.json、keyframes/laugh.json、quack.py(416行)。

控制环要点：
- 走路/站立按速度阈值自动切；坐站/叼取/踢由 robotd 调度器显式选；共享 61 维契约；LSTM 额外传 hidden/cell。
- 「一切在加载时验证，不在推理时验证」——错 bundle 必须在站着不动时失败，否则 60 拍（~0.5s）后在迈步中途崩。
- ONNX Runtime 两个坑：缺 dylib 时 ort 不返错而是 setup_api 里 expect → 线程死 → robot.health 只说「循环没完成一个周期」；探测通过也照样 panic（板上 ORT 1.20.1 vs 要求的 1.23），所以有 catching_ort_panics。
- 推理线程故意=1：四核 A55 上控制线程会被不拥有的线程池阻塞，小网络同步开销 > 并行收益。
- 安全层：三道独立限位（非有限值/行程/deadman）+ 三个独立计数器；日志首次必报、之后每 50 次一行；计数器在「到达检查且未触发」时清零，语义是「持续了多久」。NaN 的 tick 在钳位前返回，故意不清零 range 计数器。
- 诚实边界：XL330 的 range 是执行器一转，不是解剖关节限位。

情感要点：
- 10Hz 关键帧、13 字段、增量制；mouth 已与声音预先同步。
- laugh = 3.0s/30 帧：0-0.4s 抬头+甩头，0.5s 首声长 haaa，1.1-2.5s 七声短 ha 且 mouth 峰值递减 1.0→0.49。
- sad 的 robot_note：「故意只做一半深度，更深的低垂会把头部质量前移，真鸭子会往前走一步」——表达幅度被平衡约束直接砍。
- 声音：quack.py 精确移植 Rust RNG（splitmix64+xoshiro256++），ROBOT_SEED=4145077059 是嗓音身份；contour/env/mods 三个概念；48kHz。
- devastated 是唯一 sound_at_s=0.3 的（先坐下再反应）。
- 设计史在 git tag workshop-2026-10-07；播放走 pad-expressions.patch，D-pad Up 进情绪模式，短按<0.6s。

## 横向对照（第五轮，microduck-横向对照.md）

**血缘**：Microduck 是 Open_Duck_Mini（apirrone，4371★，2024-05-16）的产业化收编版。
microduck_rl 晚 19 个月，microduck 晚 26 个月；ODM README 原文「Thanks to HuggingFace and
Pollen Robotics for sponsoring this project」。星数 10111:4371 差的是产品化，不是原创性。

**BAM 的 params 目录有 9 款电机**（`bam/params/`，这是选型白名单，别再自己辨识）：
erob80_100 / erob80_50 / feetech_sts3215_7_4V / mx106 / mx64 / waveshare_st3025 / xl320 / xl330
→ **修正上一轮结论**：飞特路线不是死路。HD-1910 不在清单（需自辨识），但 **STS3215 官方有参数，
且 ODM 已用它跑通完整 sim2real**。

**XL330 vs STS3215-7.4V（m1 模型）硬差异**：
kt 0.371 vs 1.178（3.2×）｜armature 1.6e-3 vs 2.6e-2（**16×**）｜friction_viscous
3.9e-3 vs 6.0e-2（**15×**）｜command_delay 5.93ms vs 1.05ms（**1/5.7**）｜q_offset 符号相反。
→ 「参数一行都不能抄」有硬证据；q_offset 符号反这类只能辨识不能推理。

**最重要的反面证据**：`kabilankb/isaaclab-microduck`（Isaac Lab 3.0 + Newton 移植）明确写
「BAM actuator / observation delays / encoder bias 尚未移植 → locomotion 收敛到站着不动」。
即这三样不是 DR 锦上添花，**是走路能否成立的必要条件**；去掉连仿真里都学不会。
它还补了官方没明写的观测契约：61D = 48D 本体 + 13D `[twist(3), head_pose(4), body_pose(6)]`，
以及双机任务用 frozen partner（共享网络会把观测翻倍→不可部署）。

**两种奖励范式的本质差别**（最有复用价值的一条）：
Microduck 把「什么是好步态」放在**奖励函数**里 → 必须自己堵所有漏洞（三次翻车的来源）；
ODM 把它放在**参考动作**里（Disney BDX imitation reward + parametric walk engine）→ 漏洞天然缓解，
但行为被参考框死。两者不冲突：Microduck 的 61D 观测里 head_pose/body_pose 正好是参考动作通道，
可直接叠加 imitation reward。BHL 有 mocap 遥操作 → 能自己产参考动作，Microduck 没有 → 只能走奖励工程。

**硬件缺口是主动放弃，不是遗漏**：ODM 有 Onshape 可编辑 CAD + `onshape-to-robot` 一键导出 + BOM
（含中文飞书镜像）+ 装配指南；Microduck 只有 47 个 STL，机械 CC BY-SA-**NC**（禁商用），
BHL 资产是 CC BY-SA 4.0（可商用）。差一个 NC 决定能不能做产品。

## 低成本方案（第七轮，microduck-低成本方案.md）

**核心结论（反直觉）**：成本低+效果好 ≠ 复刻，而是「今天 ¥0 跑通全链路 + 12 月买 $399 整机」。

**三笔账**（关键数字，来源 GavinHome/microduck-replica/docs/执行器选型.md）：
- 官方整机 $399 ≈ ¥2850（含运税 ¥3200–3600），25cm/737g，开箱能走
- XL330 自攒：¥299×15=¥4485，现货溢价 **¥9700–11000**，总 ¥6000–13000（整机 2–4 倍，纯溢价）
- STS3215 自攒：**¥60–70**×15≈¥975（XL330 的 1/5，力矩还更大 1.86 vs 0.96 N·m），总 ¥2500–3000

⚠️ **关键约束：便宜舵机塞不进 25cm**。STS3215 重 3 倍（55–60g vs 18g）→ 同一工程师
（Antoine Pirrone，Pollen R&D，也是 ODM 作者）换舵机后整机只能做成 **42cm / 2107g**（就是 ODM v2）。
即"Microduck 降本复刻"会自动变成"再造一台 ODM"，而 ODM BOM 也标 $400。
MJCF 参数差数量级：kp 0.55→17.8（32×）、armature 0.0018→0.028（15.5×）、damping 11×、frictionloss 11×。
→ 「改舵机不重训」必然失败。

**零成本路线（已实测验证）**：`tailong-wu/microduck-mjbatch`
```
uv sync
uv run train_ppo.py --task velocity --num-envs 4096 --iterations 1500 --timestep 0.005
```
**8 vCPU / 2h36m / final reward 4.10 / tracking 0.95 / 零摔倒**（机器里的 2080Ti 全程没用）。
不需要 CUDA，命令只有两条，结果被明确标 solved。这是「成本低」的真正答案。

**三阶段**：0) ¥0 纯 CPU 训 + golden vectors 校验 + 官方 WASM 沙箱看效果；
1) ¥299 买 1 个 XL330 跑官方 `xl330_test_bench` 单舵机辨识（性价比最高的一次花钱）；
2) 12 月 ¥2850–3600 官方整机，热插拔阶段 0 的 ONNX。合计 ¥3200–3900。

**替代**：现在就要真机 → 做 ODM v2（¥2500–3000，42cm，有 Onshape CAD + BAM 现成 STS3215 参数 + 可商用许可）。
**别做**：XL330 溢价复刻；把便宜舵机塞 25cm；从零复现官方复合技能（私有 teacher，HTTP 403）。
**效果验证**：golden vectors / xinhuagu 开放考试（256 鸭×3 seeds，官方策略在同表）/ arena。
⚠️ 官方 `error_vel_xy` 高估约 3 倍，任何"误差 0.2"都要问口径。

## 第三轮：把延迟训进去（三个负结果）+ 两个工具 bug

### 结论先行
没有拿到可宣称"更好"的权重。阶段 A（`out/robust61_a.pt`）在真实传感器模型下前进 0.395、
基线 0.159，但后退/侧移/转向全面退化（后退 −0.147，即走反了）。是能力置换，不是帕累托改进。

### 三个负结果（都可复现）
1. **热启动不能用默认 LR**：`train_ppo.py` 的 `LR=1e-3, EPOCHS=5` 是给从零学走调的。
   对已会走的策略，16 轮内 reward 3.71 → −0.35。热启动应 2.5e-4 + 3 epochs。
   → 已给 `train()` 加 `lr/lr_end/epochs` 参数，`train_robust.py` 加 `--lr --epochs`。
2. **奖励分不清站着和走**（最重要）：`track = exp(-|v-cmd|²/SIGMA)`，`SIGMA=0.25`，
   所以恒定 0.3 m/s 下**站着不动就有 0.698 分**。而 gait/upright/pose/height 全在奖励静止姿态。
   后果：加随机化后 reward 只掉 3.84→3.71，实测速度 0.127→0.085，"干净"条件 0.136→0.005。
   `--track-weight 3` 能止损（0.132）但超不过阶段 A。
   **教训：训练日志的 reward 不能用来判断"在不在走"，必须另测恒定命令下的 m/s。**
3. **策略对"哪些通道被延迟"极敏感**：同一策略，只滞后关节速度 → 0.066 m/s；
   陀螺+重力也一起滞后 → 0.395 m/s。两者物理上都只是 20 ms，差 6 倍。说明它在利用特定
   延迟下的相位关系，不是在容忍延迟。

### 两个工具 bug（都已修）
- `tools/robustness.py` 转向跟踪率：`denom=abs(cmd[2])` 但 `yaw_rate` 有符号 →
  负向转向命令正确跟随也恒为负、永远 FAIL。修法：`rate = yaw_rate * sign(cmd[2])`。
- `tools/envelope.py`（新工具）`sweep` 在 19 个命令点之间**不 reset env**，后一个点从上一个点
  的终态开始。6 秒时污染小、12 秒时全崩，害我一度以为策略坏了。修法：每点前 `env.reset(arange)`。
  ⚠️ 通则：任何"扫一组条件"的工具，条件之间必须显式 reset。

### 56 维 vs 61 维：终于有可比结论（`tools/envelope.py`，19 点 × 12 s × 12 envs）
两者都过 15/19，但**能力形状不同**：61 维中高速前进强很多（+0.50: 0.883 vs 0.555；
+0.60: 0.883 vs 0.177），56 维转向强（+0.30/0.60/0.90: 1.14/1.08/1.05 vs 0.78/0.88/0.93）。
0.30 m/s 这个常用工作点几乎一样（0.706 vs 0.776），所以"56 维更准"在这个速度上不成立。
两者共同短板：**+0.10 m/s 跟不动** → 步态有最低速度死区，真机摇杆需要死区。

### 56 维不可部署有两个独立原因（别再混成一句）
1. `base_lin_vel`（真机测不到，上游是显式删掉放 critic 的）
2. **最后两维是 `sin(clock)/cos(clock)`，步态时钟进了观测**——`obs.rs` 的 61 维契约里没有这通道
   （`train_ppo.py` OBS_DIM = 3+3+3+3*14+3+2，多出的 5 = 3 命令 + 2 时钟）

### 延迟单位的更正（之前写错过，已改文档）
mjlab `DelayedActuatorCfg` 文档原文：「Delays are quantized to physics timesteps (not control
timesteps). ... a lag of 2 represents a 4ms delay」。所以上游 `delay_min_lag=3, max_lag=6`
在 500 Hz 物理下是 **6–12 ms**，不是 60–120 ms。旁证：真机确实能走，而 60–120 ms 我们实测必摔。
⚠️ mjlab v1.1.1 已**删除** `DelayedActuatorCfg`，延迟改成写在任意 `ActuatorCfg` 上。照老名字搜不到。

## 第四轮：奖励核宽度是三件事的共同根因（纯分析，零训练成本）

### 一句话
`--track-weight` 和 `SIGMA` 不是一回事，前者改不了「站着 vs 走」的比值。

### 推导
`reward ∝ w · exp(-d²/SIGMA)`，`w` 乘在整项外面 ⇒ 「站着」/「走对」比值恒为 `exp(-d²/SIGMA)`，
与 `w` 无关。所以 `--track-weight 3` 只能抵消 gait/pose/upright 的静止偏好（那是第 2 个问题），
修不了「kernel 太宽」（第 1 个问题）。这解释了为什么 v2 只从 0.004 回到 0.132、超不过 A。

### 数值（cmd=0.3, 站着 v=0, d²=0.09）
SIGMA 0.25→0.698 / 0.10→0.407 / 0.05→0.165 / 0.02→0.011

### 新结论：低速死区和奖励崩塌是同一个根因
`tools/envelope.py` 早先测出 56/61 维**都在 +0.10 m/s 跟不动**，当时归因为「步态最低速度死区」。
算完才看清：**0.1 m/s 命令下站着不动得 0.961 分**。策略不是走不了慢，是奖励说「最正确的做法就是站着」。
→ 修正一个认知：这不是步态能力问题，是奖励形状问题。
→ 且收窄 SIGMA 也救不了低速（0.05 时站着仍 0.819）。**绝对宽度的核在变速命令下必然产生低速死区**，
   正解是相对误差核（按 |cmd| 归一化）。上游同样用绝对核 ⇒ 上游也有这个死区，
   和「真机摇杆必须留死区」是同一件事，不是两个 bug。

### 文档修正（README 411 行）
- 新增「加权重救不了，改 SIGMA 才可能救」+「低速死区」两小节
- 修掉过时表述「jvel_lag 无条件开启，不进随机化范围」→ 已改为概率 0.5，并写明原因（策略会反过来依赖滞后）
- 「已知缺口」新增第 1 条（且标注为最大实质缺口）：**目前没有任何权重同时满足真实部署条件 + 全向机动**

## 第五轮：奖励形状三种改法全试完，阶段 A 仍是上限（含一个必须记的测量陷阱）

### 最重要的更正：deploy61 在真实传感器路径下根本没站住
`tools/ab_compare.py`（新工具）加了倾角列之后一眼看穿：deploy61 在 official 下**6 个命令的
倾角全部 45–46°、10 秒摔 46 次**。它那些看起来更优的跟踪率（yaw 1.63、back 1.19、side 0.98）
全是**翻倒过程中的位移**。
→ **通则：跟踪率是沿命令方向的净位移，不区分"走过去"和"滚过去"。必须和倾角/摔倒数同屏读。**
→ 我上一轮写进 README 的"阶段 A 是能力置换"结论**由此作废并已更正**：不是置换，是基线不可用。

### 三种奖励改法的完整对照（official 传感器模型，12 envs × 10 s）
| 命令 | deploy61 | robust61_a | robust61_s | robust61_n |
|---|---|---|---|---|
| fwd .30 | 0.16 (45°) | **0.39** (6.4°) | 0.24 | 0.05 (14.8°) |
| fwd .50 | −0.03 (46°) | −0.11 | +0.02 | 0.23 (46°,11摔) |

### 我的实验设计错误（比结果更值钱）
`--track-weight N` 只乘 `REWARD["track"]`，**不乘 `REWARD["turn"]`**。两者是同类任务奖励。
实测：turn 从 A 的 0.24 → v2 0.19 → S **0.08**，对应转向能力 0.78 → −0.03。
→ **S 那一轮不能用来判定"收窄 σ 有没有用"**，它同时改了两个变量。
→ 通则：**任何"加权"改动，先问清它乘了哪些项、没乘哪些项。**

### 正确解法：基线归一化（已实现为 --track-baseline）
`t' = (exp(-d²/σ) - exp(-|c|²/σ)) / (1 - exp(-|c|²/σ))` → 站着恒 0、走对恒 1，与 σ 和命令大小无关。
顺带解决低速死区（0.1 m/s 下站着也是 0，不再是 0.961）。
两个**必须**的保护，都是先炸了才加的：
1. **零命令要掩掉该项，不能给分母下限**：`cmd_yaw=0` 时分母 = 0，钳到 1e-3 后偏航噪声 0.3 rad/s
   被放大成 **turn −287**，第一轮就崩。
2. **结果裁到 [-1,1]**：0.1 m/s 命令下分母仅 0.039，走反得 **−15** 并被 FLOOR 截断；且无界惩罚
   会让策略宁愿站着(0)也不愿尝试(±1)，正好反噬这个改动的目的。

### N 的失败给出一个控制论结论（本轮最有价值的洞察）
| | clean | official | 落差 |
|---|---|---|---|
| robust61_a | 0.42 | 0.39 | 1.1× |
| robust61_n | **0.85** | 0.05 | **17×** |
归一化把梯度做陡（0.3 m/s 时分母只有 0.30），逼出**高增益**策略：无滞后时能精确跟 0.85，
有滞后就振荡（前进 0.3 倾角 4.8°→14.8°，0.5 直接 46° 摔 11 次）。**高增益控制器对延迟敏感是
控制论必然，不是训练没收敛。**
→ **阶段 A 的"慢"不是缺陷，是它换取延迟下稳定性的代价。**
→ 「走得准」与「延迟下走得稳」在这个植物上互斥，奖励的精度要求决定策略落在哪边。
→ **这条路的上限就是阶段 A**。三种改法从三个方向撞过，瓶颈不在奖励形状，在"有延迟观测下
  精确跟踪"本身需要更多训练量或延迟课程 —— 不是"再跑一轮"能解决的。

## 三项目互借 + 网上印证（产出 `microduck-三项目互借与网上印证.md`，299 行）

### 最重要的结论：优先级错了 —— 我们在随机化错的东西
Tan et al. Ghost Minitaur（Sim-to-Real: Learning Agile Locomotion）原文结论：
**"high-fidelity simulation is more critical than extensive randomization; without accurate
actuator and latency modeling, policies failed to transfer regardless of robustness training."**
对照 `repo/train_ppo.py:87-92`：`set_to_position(kp=KP, kv=KD)` + 常数 forcerange
⇒ **执行器带宽无穷大，力矩说给就给**。在这样的植物上随机化命令延迟，教不会策略"力矩要等一会儿"。
→ 缺失的 BAM M6 电压模型**不是保真度加分项，是这条路由的前置条件**。优先级高于再跑奖励改造。
→ 同时解释了"同样 20 ms、不同通道差 6 倍"：策略在依赖瞬时执行做相位补偿。

### 第二条：延迟容限有公式，能反推带宽
`T_d,max ≈ PM_rad / ω_gc`（Atlas of Engineering 相位裕度页），且"增益↑ → 相位裕度↓"。
这给出了上一轮那个 17× 落差的**理论解释**（归一化核 → 高增益 → ω_gc↑ → 延迟容限↓），
不再只是我凭直觉说"高增益必然敏感"。
反推：我们 40–60 ms 的悬崖 ⇒ ω_gc ≈ **1.5–3 Hz**。这个数可独立测（扫频/方波），
测出来就能 10 秒预测延迟容限，不必跑 27 项阶梯。**可证伪的下一个实验。**

### 第三条：负对照（这条最便宜、最该现在做）

## 第六轮：硬件方案定稿，并推翻此前自己的舵机选型

### 最重要：S288 那个 0.6 N·m 是错的，我此前把它排在第一
宇树官网桌面版参数表（unitree-robot.com/cn/DigitalServo/）自己写：S288 堵转 **反向 0.2 / 同向 0.07 N·m**，
最大线电流 0.32 A，扭矩常数 0.554 N·m/A → 0.554×0.32 = **0.177 ≈ 0.2**，自洽。
首页/移动版那个「0.6 N·m」和它自己的电流限值矛盾。雪球独立复盘也写「S288 反向最大 0.20Nm」。
→ **S288 是扭矩 1/4，不是「更便宜且更强」。** 另：12.6V 供电 + Unitree 私有 6Mbps 协议（非 DYNAMIXEL 2.0），
  寄存器/控制语义全不同，不是可替换件。

### 第二个大发现：XL330 是**超压**跑的
官方规格 3.7–6.0V / 推荐 5V / 堵转 0.52 N·m@5V。**真机喂 6.6–8.2V。**
硬证据：`pollen-robotics/elec_RPI_Robot_HAT`（Apache-2.0，97★，2026-10-20 更新）原理图里
Dynamixel 插座 J11/J13/J14 电源脚直连 `+BATT`，经 TH1 100R，**中间无稳压**；整板 47 行 BOM 只有一个
buck（U9 AP63205 2A）+ 一个电感，输出 +5V 只去 Pi 排针/音频/EEPROM。
→ **舵机轨不能稳压**，稳压到 6V 掉 25–30% 扭矩，而策略是按 8V 训的。
→ 这解释了 `tools/plant.py` 的 `FORCE_STALL = 0.96`：0.52 × (9.2/5) ≈ 0.96。
→ 也解释了上游电压自适应 `scale × (7.4/实测EMA)` 和 6.6V 自动坐下。
→ ⚠️ 由此推出一条上机纪律：**第一次站立必须 ≥8.0V**，7.2V 以下变差是物理必然，会被误判成策略坏了。

### 第三条：官方 HAT 是开源的（此前报告说「硬件不开源」不准确）
`elec_RPI_Robot_HAT` Apache-2.0，含 `elec_RPI_Robot_HAT.kicad_pcb` + 5 张分图
（power/dynamixel/audio/sensors/pwr_supply_charge）+ `production/` → **可直接打样**。
真正不开源的只有 **imu_to_dxl 板**（LSM6DSV16X + MCU + 半双工收发器，总线 ID 200，12 字节块 =
陀螺 i16 ±500dps + **芯片内 SFLP fp16 四元数**，主机不跑融合）。

### 总线时延预算（自己算的，估算值）
1 Mbps、16 设备、12 字节块：SyncRead 30B + 16×22B 状态包 + 换向 0.32ms + SyncWrite 80B ≈ **4.9 ms**，
占 20 ms 的 **25%**。
→ 解释了为什么是 50 Hz 不是 100 Hz（100 Hz 时占 49%，无余量）。
→ **出厂默认 57600 必须改成 1 Mbps**：同样事务在 57600 下 ≈80 ms = 4 个控制周期，根本跑不起来。
   现象是「舵机能动，一走路就抽」。X 系列出厂默认 57600。

## 第七轮：只有一块 ESP32 时能做什么（新增 export_mcu.py）

### 核心结论
ESP32 **够做控制环，不够做视觉和对话**。actor 只有三层全连接：
25,984 MAC，103.0 KiB flash，240 MHz 下 **0.54 ms = 20 ms 周期的 2.7%**。
→ 算力从来不是瓶颈；瓶颈仍是舵机（¥3600 占 90%）和缺合格权重。

### 新工具 `tools/export_mcu.py`（已跑通）
`--policy out/robust61_a.pt --out out/mcu` → 纯 C99 的 `policy.h` + `selftest.json`。
两个独立验证，都过了：
- **字面量回读**：从生成文件里正则读回 26,376 个数，逐位比对 → 全部 bit-exact
  （抓 `%.9g` 精度丢失 + `carray()` 自身 bug，自洽比较抓不到这个）
- **累加顺序差**：torch(BLAS) vs `cumsum([bias,t0,t1,...])` 同顺序实现 = **3.8e-06**
  → 必须自己实现一遍 `seq_forward`，直接和 torch 比等于把误差藏起来。

### 一个会静默出错的布局更正（重要）
61 维最后 13 维**不是"命令+填充"**：
`[48..51)` 速度命令 3 维，`[51..55)` **头部命令 4 维**，`[55..61)` **身体姿态命令 6 维**。
后 10 维训练中**全程为 0**（env cfg 把 head 固定 home、body 固定 nominal）。
部署时填非零 → 离开训练分布，但**网络仍输出看起来合理的动作**，只在真机表现为"走得怪"。
→ 以后要做头部跟踪，这两段必须重新训练，不是填进去就行。

### 新发现：极端输入下动作会爆到 11 rad
`stress_fall` 向量（陀螺 4 rad/s、关节速度 8 rad/s、关节角 π）→ |action| = **11.0 rad**。
这两个值都**物理真实可达**（跌落时；XL330 上限约 10.9 rad/s），不是人为夸张。
→ 上游 safety.rs 只拒绝 NotFinite，抓不住"传感器掉线报 0"（零陀螺/零重力都是合法浮点）。
→ 已在 C 里加 `md_obs_ok()`：检查 |g| ∈ (0.5, 1.32)。窗口依据：训练重力噪声 σ=0.01，
  实测 |g| 在 1.00±0.02，而直立时 |g| 恒为 1。

### ESP32 存在的真实优势（此前没意识到）
Radxa Zero 3W 跑 Linux，50 Hz 定时器抖动是 **ms 级**；ESP32 裸机/RTOS 是 **µs 级**。
这个抖动直接落进 `act_delay` 的下界——而 act_delay 正是我们实测最脆弱的那个轴
（40–60 ms 悬崖）。⇒ 用 ESP32 不是"降级凑合"，在延迟这一项上它可能比原方案更好。
另外 ESP32 还能吃掉 imu_to_dxl 那块板（自己挂 IMU 自己跑融合），省一块打样。

### 代价（必须说清）
失去 IMX219 视觉 + 云端 Qwen 对话。ESP32 能做麦克风采集 + WiFi 上传，但延迟和体验差一档。
→ 若目标是"完整 microduck 体验"，ESP32 不够；若目标是"先让它走起来"，ESP32 完全够且更简单。

## 第八轮：回头查"凭什么相信之前的数字"，查出三个静默 bug

用户问「板子的先放一放，项目还有需要优化的地方吗」。没有再训策略，先审测量工具。

### bug 1（最严重）：动作延迟永远少一格，`latency_20ms` 就是 `nominal`

发现方式不是读代码，是**两个本该不同的条件给出了一模一样的数**（0.458/6.0°/17° 全同）。
`robustness.rollout` 的延迟线写成 `deque([zeros]*act_delay, maxlen=act_delay)`：往已满的
deque 里 append 会先挤掉最老的，`popleft()` 拿回的是**刚 append 进去的那个** action。
正解 `maxlen=act_delay+1`。

→ **此前所有 `latency_*` 条件的名字都比实际延迟大 20 ms。** 修后 `robust61_a`（8 s×8×3 seeds）：
0 ms 0.438｜20 ms 0.396｜40 ms 0.388／0 摔｜60 ms 0.245／**29 摔**／倾角 47°｜80 ms 0.503／56 摔。
→ 结论从"60 ms 以内有救"改成"**40 ms 以内有救，60 ms 摔**"，和训练时 `act_delay=(0,2)` 自洽。
→ 顺带：`latency_80ms` 跟踪率 0.503 比 60 ms 还高却摔 56 次——"高跟踪率=在摔"第三次复发。
  现在 `robustness` 给摔倒过的行打 `*`，脚注逼读者先看 falls/tilt。

### bug 2：观测历史在 `obs()` 里推进，有效延迟取决于别的机器人摔不摔

`train_ppo.rollout` 在任一 env reset 的那步会调 `obs()` **两次**，而 `train_robust.Duck`
每调一次就推一格历史 ⇒ 全 batch 多推一格，`d_obs=1` 悄悄变 2。
修法：推进移到 `step()`，`obs()` 变纯读。同时修 reset 时 `act_hist` 不清零
（`d_act=2` 的环境 reset 后会重放倒地前的最后两个动作）。

### bug 3：`plant.py` 改了质量，没告诉求解器

### 最重要的修正：我们的 SIGMA 两个方向都错了

`train_ppo.py` 原来 `SIGMA = 0.25` 同时给 track 和 turn 用，注释还写着"upstream 0.25"。

|---|---|---|---|
| 线核 | 0.10 | 0.25 | 宽 2.5×，站着对 0.3 m/s 得 0.698（上游 0.407）|

## 第十二轮：第五个（第四个）静默 bug —— 权重 1.0 的 gait 项一直在送常数

给 `--air-time` 做完想验证它，才发现脚高恒为 0。往下查是环境本身的 bug。

### bug 本体

`train_ppo.Duck.__init__`：
```python
self.foot = self.site[:, self.feet]     # self.feet 是 list → fancy indexing → 复制
self.rot  = self.xmat[:, self.trunk]    # self.trunk 是 int  → basic indexing → 活视图
```
`site_xpos` 只由 `mj_forward`/`mj_step` 写，`__init__` 在两者之前跑 → 复制的是**全 0 缓冲**，
之后永不更新。

`height = self.foot[:,:,2]` 恒为 0 的后果：
- `stance = exp(-(height/0.01)²)` ≡ 1
- `high = max(height-CEILING, 0)` ≡ 0
- `gait = blend·swing + (1-blend)·stance` → **只依赖相位时钟的纯时间函数，零梯度**
- **照样打印 0.83**

### 回答用户的问题「找了这么多参考，怎么还有大 bug，资料不够多吗」

不是资料量的问题。5 个静默 bug 分类：

  fancy indexing 复制 vs basic indexing 视图 / `dict(DEFAULTS, **cfg)` 把未写的轴补回默认 /
  `obs()` 有副作用。这类 bug 发生在**我写的那一行**，外部资料不可能覆盖。
- **1 个是「资料里有、我没查」**：改 `body_mass` 后要 `mj_setConst`。这个算是资料没查够。

真正的共同特征：**5 个全都通过了「看起来合理」这一关**。
`latency_20ms == nominal`（像"影响不大"）、`gait 0.83`（像好步态）、`track 0.79`（像在走）、
`body_invweight0` 错 63%（物理还能跑）。**静默 bug 的定义就是输出落在合理区间。**

资料真正的价值不是防 bug，而是**提供"应该是什么"，从而让"实际是什么"可比较**。

上游有 `AGENTS.md` 错题本，是因为他们被物理世界打脸了很多次；我们没有那个反馈源。

## 第十四轮：奖励还有三处公式错，以及「原地踏步」这个新失效模式

用户说「按最优的来」。最优是**一次性把奖励对齐上游**，而不是等 k1 跑完再逐项补。

→ 策略学会了**原地踏步**：`air_time` 只要求脚离地 125–300 ms，不需要真的移动，

**这是第 6 个同类教训：每个奖励项都要问「有没有一种退化行为能单独刷满它」。**

### 三处公式错，全在正则项，全让「姿态松」变便宜

把上游 `microduck/tasks/mdp.py`（7706 行）里的实现逐行读出来，不是读权重表：

| 项 | 上游 | 我们 | 后果 |
|---|---|---|---|
| `pose` | `exp(-**mean**(err²/**std²**))`，std 0.05–0.4 逐关节 | `exp(-**sum**(err²))` | 同一姿态：上游 0.64，我们 0.9 |
| `upright` | `exp(-err/std²)`，std=√0.05 → `exp(-40·err²)` | `exp(-2·err²)` | 10° 倾斜：上游 0.30，我们 0.98 |

`pose` 最紧的是 `hip_roll` 的 **0.05 rad**（`microduck_velocity_env_cfg.py:199-217`）：
(0.05/0.05)² = 1 个 e-fold。我们那版同样误差只值 0.0025。
`upright` 直接漏了 `/0.05` —— 把「直立」从约束降级成装饰。

**加上权重全线偏小**：track 1.0(2.0)、turn 0.5(2.0)、pose 0.5(1.0)、upright 1.0(2.0)。
正项 4.5 / 负项 −1.605 = **2.8**；上游 10.0 / −1.27 = **7.9**。惩罚相对重 2.8 倍。

### 实现 `--upstream-rewards`

一个开关做三件事：
1. 权重照抄（track 2 / turn 2 / pose 1 / upright 2 / air_time 3 / rate −0.1）
2. `pose` 换 `exp(-mean((q-q_stand)/std)²)`，`speed<0.01` 时切 standing std，否则 walking
3. `upright` 补 `/0.05`
4. **上游没有的项清零**：gait / height / slab / torque / limits

`POSE_STD_STAND/WALK` 按我们模型 14 关节顺序硬编码：
`[hip_yaw .1, hip_roll .05, hip_pitch .15, knee .15, ankle .1, 头×4 .3, 右腿同]`（walking: .3/.05/.4/.4/.25）
头 4 个是我们补的（上游 `head_pose` 是活动目标所以没有 std，我们 head_cmd 恒 0，给 0.3 防漂移）。

**踩到一个广播坑**：`np.where(speed < 0.01, STD_14, STD_14B)` 报
`operands could not be broadcast (4096,) (14,) (14,)` —— cond 要 `[:, None]`。
**和 foot 缓存 bug 是同一类**（numpy 索引/广播语义）。冒烟测试抓到，代码审查看不出来。

### `selfcheck.py` 加两个公式钉子（25/25）

- `pose`：0.1 rad 均匀误差下，上游核必须比 `exp(-sum)` 严格 > 30%（0.362 vs 0.869）
- `upright`：10° 倾斜必须 < 0.35（旧版 0.941）
理由是**这两个 bug 的失效模式是「数字看起来合理」**，必须数值化钉住。

`robust61_u1` = `--init robust61_a --upstream-rewards`，600 iter，约 50 分钟。

u1 启动后 15 iter：`track 0.71–0.72`、`reward 4.82`（在涨）、19k steps/s。

### 顺带确认

- `turn` 现在是 weight 2.0 × 核 0.50 → yaw 误差 1.0 rad/s 得 **0.27**，最初是 **0.009**。
  **转向信号强 30 倍。** 这是第一次「策略不会转」不能再赖奖励。
- `gait` 清零是唯一有代价的：667 ms 参考时钟没了，步态只能从 `air_time` 涌现，

## 第十五轮：我自己的修正过度了 4 倍，而自检抓不到

这一轮最值得记的不是 bug，是**我的自检写错了断言形式**。

### 事件链

1. 发现 `upright` 旧版 `exp(-2·up_err)` 比上游松 5 倍 → 决定修。
2. 修成 `exp(-2·up_err/0.05)`。**保留了那个 2，又加了 /0.05。**
3. 自检写 `check("10° 必须 < 0.35", tight < 0.35)` → **通过**（因为它确实变严了）。
4. `robust61_u1` 训到 194 iter，`v` 只有 7%、`air_time` 掉到 0.02，**比修之前更保守**。
5. 回头算才发现：上游的 `err` 是 `tilt_sq = 1−cos(tilt)`，我们的是 `sin²(tilt)`，
   **两者差整 2 倍**（10°：0.0152 vs 0.0302）。所以 `tilt_sq = 0.5·up_err`，
   正确写法是 `exp(-0.5·up_err/0.05)`。我的是 `4×tilt_sq/0.05`，**严 4 倍**。

| 倾斜 | 上游 | 旧版（松） | 我的错版（严 4×） | 正确版 |
|---|---|---|---|---|
| 5° | 0.927 | 0.985 | 0.738 | 0.927 |
| 10° | 0.738 | 0.941 | **0.299** | 0.740 |
| 15° | 0.506 | 0.918 | **0.069** | 0.512 |

走路是"一系列可控的倾倒"，10° 倾斜被重罚 0.70×2.0=1.4（而 track 满分才 2.0），
策略只能站着。**所以"改对了方向"和"改对了幅度"是两件事。**

### 自检的缺陷（核心教训）

原来的断言：`tight_up < 0.35` —— 断言"朝正确方向变化了"。
改成两条：
```python
check("upright matches upstream's 1-cos(tilt) kernel at 10 deg (within 2%)",
      abs(ours - upstream) <= 0.02*upstream, ...)   # 0.740 vs 0.738 ✓
check("upright is stricter than the legacy exp(-2*up_err)",
      ours < legacy - 0.15, ...)                     # 0.740 vs 0.941 ✓
```
**第一条是等价性断言，会在 0.299 vs 0.738 时立刻红。**
→ 通用规则：**从参考实现移植公式时，断言必须比对"数值与参考的等价性"，
不能比对"相对被替换版本的变化方向"。方向对 ≠ 幅度对。**

### 差点犯的第二个错：up 的定义

一度以为 `up = -rot[:, 2]` 取错了轴（应该是 `-rot[2, :]`），因为靠手推 `R^T @ [0,0,-1]`
一直在两个结果之间摇摆。实测：倾斜一个 env 10°，与 `R.T @ [0,0,-1]` 比对 → **完全相同（1e-6）**。
**代码是对的，是我探针写错**：`rot[0][:, 2]` 是 2D 数组的列，`rot[:, 2]` 是 3D 数组的行。
又一次 basic-vs-advanced indexing 陷阱，这次在我自己的探针里。

### 观测契约审计：通过（主动验证，不是碰巧）

发现有两套环境类，一度以为布局冲突：
- `train_ppo.Duck` = **56 维**，含 `sin/cos(clock)` 两列 + 预缩放（2*vel, 0.25*gyro, 0.05*qvel）
- `train_official.Duck`（子类，替换 obs）= **61 维部署契约**：
  `gyro(3) | gravity(3) | joint_pos−stand(14) | joint_vel(14) | action(14) | command(13)`
  无时钟、无预缩放、joint_pos 相对、command = 3 twist + 4 head 零 + 6 body 零

`train_official.py:56` 有 `assert 3+3+14*3+3+4+6 == 61` 钉着。
`train_robust` 用 `T.TASKS["velocity"] = (Duck, ...)` 注册，所以训练走 61 维类（读注册表确认）。
**观测侧没有缺陷，缺陷全在奖励侧 + foot 缓存。**

## 第十六轮：用户一句「网上没有正确的数据吗」把整件事掰回来了

问得对。前几轮我一直在**从文字反推数值**，而数值本身就在两个公开包里：

- `pollen-robotics/microduck_rl` @ **`develop`**（注意：`master`/`main` 都 404）
  `src/mjlab_microduck/tasks/microduck_velocity_env_cfg.py:275-356` = 任务级权重与 std
- PyPI `mjlab==1.3.0`，解 sdist 后
  `src/mjlab/tasks/velocity/mdp/rewards.py` = 全部奖励核
  `src/mjlab/tasks/velocity/velocity_env_cfg.py:275-371` = 基础奖励表
  `src/mjlab/entity/entity.py:787` = `gravity_vec_w = [0,0,-1.0]`

整理成 `microduck-software/.upstream/UPSTREAM_REWARD_SPEC.md`（带 file:line）。

### 三个真错

1. **`upright` 我错了两遍，两次自检都同意我。**
   我把上游读成 `tilt_sq = 2(qx²+qy²) = 1−cos`，于是给 `sin²` 乘 0.5「换算」。
   源码既不用四元数也不用 1−cos：投影重力的 xy 平方**就是** `sin²θ`，除以 std²，不加任何系数。
   所以那 0.5 让该项**比上游宽松一倍**（10° 时 0.740 vs 0.547）——和我推理的方向相反，
   而 `u1/u2/u3` 全都跑在这个版本上。自检之所以绿，是因为它断言的是
   `ours == exp(-(1-cos)/0.05)`，即**和我的描述比，而不是和上游比**。
   → 新规矩：移植公式的断言必须复现参考实现自己的数值。

2. **两条课程表我们完全不知道。**
   `action_rate_l2` −0.1→−1.0（0/500/750/1000/1250/1500），
   `rel_standing_envs` 0.02→0.25（0/500/750/1000/1500/2000）。
   600 iter 时 smoothing 还在 −0.2、standing 只有 5%。我们把 `rate` 冻在 −0.1 跑了每一轮，
   然后把半成品当成品评估。

### 一个决定性发现：走不直不是我们的 bug

### 新抓到的 4 处

1. **终止倾角我们严了 24°**。上游 `bad_orientation(70°)`，我们是 `up_z > -0.7` = **45.6°**。

4. **动作延迟含零延迟**。上游 3–6 物理步 @5ms = **15–30 ms**；我们 `--act-delay 0,2` = 0–40 ms，

## 第十八轮：把航向闭环打开 —— 零样本就把「走不直」修掉了

### 结论（本轮最重要）
上游实现了 `heading_command` 但**从未启用**（`rel_heading_envs = 0.0`，`heading_command`

|---|---|---|
| heading_error_deg_median | 27.8° | **4.3°** |
| lateral_m_median | 0.448 m | **0.089 m** |
| yaw_rate_median | −0.116 | **−0.016** |
| tracking_ratio | 0.359 | **0.491** |
| push_0.3mps 下 heading | 26.8° | **4.1°** |

**不需要重训。** 走不直不是容量问题、不是奖励塑形问题，是**缺了一条控制律**。

### 三个必须记住的自我修正
1. **`heading_error_deg_median` 是轨迹偏角**（`atan2(|lateral|,|progress|)`），不是偏航角。
   前三轮引用的 22.4° 意思一直是「净位移方向偏了 22.4°」，从来不是「姿态角错了」的证据。
2. **22.4° 是单种子**。同口径 16envs×3seeds 是 27.8°。所有单种子数字乐观约 25%。
   → 以后引用 3 种子；1 种子下 5° 以内当噪声。
3. **k=1 只撑到 20ms 延迟**。0/20/40ms：k=0.4 → 10.1/18.9/18.6；k=0.7 → 6.4/17.4/22.2；
   k=1.0 → 4.3/16.4/24.1。**40ms 时 k=1 比开环还差**。所以还是要训（训出来的策略会预判），
   部署延迟 6–12ms，台面 k=1 可用，真机诚实默认 k=0.7。

### 实现
- 训练 `--heading-envs F`（默认 0）、评估 `--heading-hold` + `--heading-stiffness`（默认关）
- 目标**相对**当前航向 ±45°，不是 IsaacLab 的绝对 U(−π,π)：绝对目标在 k=1 下有 68% 步数
  打满 clip，会训成「全速原地转」而不是我们缺的小误差修正。这条偏离配了负对照。
- 方法：`T.Duck.heading()`（rot[:,0] → atan2，与上游 `heading_w` 同义）、`_update_heading()`、
  `hold_heading(ids, anchor)`；评估侧 `pin(ids, anchor)` 只写线性两维，不碰 yaw 槽。

### 两个我自己的设计错（同一形状）
1. 目标不能抽在 `resample()` 里：`reset()` 先 resample 后 forward，`rot` 还是上一集的姿态。
   → 拆成 flag-then-draw，两个调用点都在 forward 之后。
2. 评估侧第一版 `pin()` **每步重锚定** = 每步把误差清零，环看着闭着实际输出恒 0。
   发现方式：第一次测量结果**逐位不变**。
   → 通用规则：看到控制律像什么都没做，先查它是不是在起作用前被重置成零了。

## 第二十二轮：为什么没用 GPU —— 根因是"自写移植"而非算力

- 硬件**有**：NVIDIA RTX 4070 Laptop，**8 GB**，驱动 CUDA 13.5。
- 但 venv 里 `torch 2.14.1+cpu` → `cuda.is_available() = False`。换 CUDA torch 也**没用**：
  仿真器是 MuJoCo **CPU 标准版**，`4096 envs × 24 horizon × 10 substeps = 98 万 mj_step/iter`
  全在 CPU；GPU 上能跑的只有 128×2 的网络（≈4 万参数、每 iter 98k 样本），瓶颈不在网络。
- **根因（真答案）**：能吃到 GPU 的正路是跑上游 **mjlab（MuJoCo-Warp）**，而我们选了
  「自己移植成纯 MuJoCo CPU」。代价是每个奖励项/观测切片/终止条件都手写一遍。
  本轮查出的全部错误（upright 少乘 0.5、`dof_pos_limits` 误零、噪声应均匀而非高斯、
  终止 45.6° 而非 70°、缺 foot_slip/swing/head_pose_bias、turn 0.55 vs 0.17）
  **没有一个是物理引擎的锅，全是重写引入的**。
- **上游依赖钉死**（`microduck_rl/develop/pyproject.toml`）：
  `requires-python >=3.12,<3.13`（BAM 钉的）、`mjlab==1.3.0`、`warp-lang==1.12.0`、
  `better-actuator-models`、`torch==2.9.1`(CUDA)、`rustypot>=1.4.2`、`onnxruntime>=1.24.4`。
  mjlab 最新 1.6.0 要 `mujoco~=3.11.0`（我们现装 3.14.0）。

## 第二十三轮：CPU+GPU 能不能一块跑 —— 不能叠加，只能分工

- **CPU 侧早就用满了**：`mjbatch.Batch(model, num_sims, num_threads=0)`，
  文档原话 "num_threads=0 uses every logical CPU, clamped to num_sims"。
  机器 **20 逻辑核**，4096 envs 已跑在 C++ 线程池上。24k steps/s 是 20 核的成绩，
  不是单核。**没有「再开一个核」的空间。**
- **同一份仿真拆给 CPU+GPU 不行**：MuJoCo CPU 与 MuJoCo-Warp GPU 是两套独立物理。
  技术上可拆成两个 env 池各自 rollout 再合并 batch（PPO on-policy，合法），
  但 GPU 那份会快 10–30×，同步时变成「GPU 等 CPU」，加速比远低于堆叠预期。
- **能落地的「一块用」是异步分工**：GPU 跑训练（mjlab，仿真+网络都在卡上），
  CPU 空出来跑评估 / robustness / ONNX 导出 / 真机串口。是不同任务，不是一个任务拆两半。
- **廉价待试**：env 数从 4096 抬到 8192，摊薄线程池固定开销，吞吐可能上去（不用改代码）。
- 环境搭建（本轮进行中）：`tooling/uvpkg/bin/uv.exe`（PyPI 装的 0.13.5，GitHub release 直下 502），
  Python **3.12.13** 在 `C:/Users/hejih/AppData/Roaming/uv/python/cpython-3.12.13-...`，

  **"走不直"这条线建立在"已有会走的策略"这个前提上，而该前提目前不成立。**
- 正确顺序：先拿到一个真会走的 checkpoint，再谈走直。要么从零训练（配 512-256-128 +
  implicitfast），要么查清站桩吸引子（`air_time` 权重 3.0 却只在落地时给分，其余项站着已接近满分）。

### 一处自我纠正（重要）

我之前反复说「站桩是奖励的 argmax」——**不准确**。算「完美走路」（vx=cmd、姿态全对、
步态在 air_time 窗口内）：OURS 约 12.0、HANNES 约 6.6，都远高于站桩。
所以站桩不是 argmax，是**「零技能可达的局部最优」**：走路路线要先从 7.36 掉到 4–6 再爬回 12，
PPO 不会先掉分。**每次"上游配方微调"都塌，是因为微调让中间过程更差、策略退回站桩。**

### DuckEMW/Hannes 配方 vs 我们（源码行号已核）

- **`forward_progress`（我们完全没有）**：`mdp.py:1292` `clamp(vx,0,cap)/cap`，
  weight 5.0，cap 2.4。三行代码，vx≤0 恒为 0，线性无天花板。**Hannes 从 0.4 走到 1.66 的骨架；
  DuckEMW 自研 sprint v1–v4 全 plateau ≤1.43，换这个才破 1.65。**
- **`heading_hold`（mdp.py:5041）**：`exp(-wrap(yaw-yaw_spawn)²/0.4²)` ×1.5。**绝对角度**锚定，
  漂了扣分、转回来加分，有方向 —— 我们 `yaw_drift` 只有速率均值，零均值摆动也满分且无回正信号。
- **`planar_drift`**：`(wz-cmd)² + 4(vy-cmd)²` × −0.05。
- 权重：head 2→**0**、upright 2→**0.75**、turn 2→**0.5**、pose 1→**0.15**、air_time 3→**0**、
  slip −0.1→−0.05、angvel −0.05→−0.01、rate −0.1→−0.02（课程到 −0.10）、
  clearance/swing target 0.02→0.015、**rel_standing 0.25→0.03**。
- **速度课程**（`microduck_running_env_cfg.py:85-93`）：0.20–0.45 起步，每 1000 iter 抬一档到 0.9–1.2，
  8750 起每 750 iter +0.15 到 2.2。**下界一起抬。我们是固定 ±0.4 = 永远在第一档。**
- **训练量 12195–13500 iter** vs 我们 2000（= 5–7 倍）。
- 他的 v1 病历（`03-training-log.md:94`）：「25% standing envs 白拿 + air_time 阶跃无梯度 +
  action_rate −1.0 摆腿税 + upright 过紧 → 无视命令站桩是 argmax」——我们全中。
  v3 的药方：**air_time 前向门控 `× clamp(vx/cmd,0,1)`**（原地腾空支付 0）+
  `init_velocity_prob=0.3` 逆向出生。

### 这一轮的推理（价值在这里）

四组对照，同一个 16 项官方表：

| | 网络 | 训练量 | 结果 |
|---|---|---|---|
| 官方 | 512-256-128 | `max_iterations` 默认 **50,000** | 出厂 alpha_walking 实测 **0.164 m/s @ cmd 0.4**，yaw 漂 >50° |
| kissqy | 512-256-128 | ~2000 轮 | **有实机、无任何量化速度** |
| 我们 | **128-128** | 2000 轮 | 站桩 0.035 m/s |
| Hannes | 512-256-128 | 12,195 | **1.659 m/s** |

→ **「奖励表抄错」可以被排除**（kissqy 逐项相同）。剩下网络容量 + 训练量。
→ 官方配方的设计上限就是 0.164 m/s，它不是「走起来」是「挪动」。
→ 我们比官方低 5 倍，这段只能由容量/训练量解释。
→ 要超过 0.164 必须加 `forward_progress`（Hannes 唯一改掉奖励结构的地方）。

**参数量实测**：128-128 = **26,254**；512-256-128 = **197,774**；**差 7.53 倍**。
