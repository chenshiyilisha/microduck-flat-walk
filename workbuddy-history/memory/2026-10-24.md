### 二、GPU 实测（这是"为什么不用 GPU"的正式答案）

`train Mjlab-Velocity-Flat-MicroDuck --env.scene.num-envs 4096 --agent.max-iterations 5`

- `device=cuda:0`，RTX 4070 Laptop 8 GiB，warp 认到 CUDA Toolkit 12.9 / Driver 13.5
- 首次启动要 JIT 编译约 40 个 kernel（`smooth` 4.8s、`ccd` 8.0s、
  `cholesky` 4.0s…），合计约 **75 秒**，一次性，之后 warp 有 kernel cache
- **稳态 3.08–3.15 s/iter**（4096 envs × 24 steps = 98,304 steps → **≈31.8k steps/s**）
- 对比我们自己的 CPU 植物：20k steps/s、4.9 s/iter（20 核已吃满）
- → **GPU 是 1.6 倍，不是数量级**。原因：microduck 只有 20 DoF，4096 envs 在 4070 上
  并行度不够，每 iter 还有固定 Python/RSL-RL 开销。
- **真正的价值不是更快，是把 CPU 腾出来了**：GPU 跑时 20 核全空，
  「CPU + GPU 一块跑」到这里才成立（两个独立实验并行）。

### 61 维契约（这次彻底钉死，全部一手）

`base_ang_vel(3) + projected_gravity(3) + joint_pos(14) + joint_vel(14) + actions(14)`
`+ twist(3) + head_command(4) + body_command(6) = 61`。
- term 顺序来自补丁 `tests/test_joy_cfg.py:242` 的断言（不是猜的）；
- head 4 维 / body 6 维来自 `joy_head_command` / `joy_body_command` 的返回形状
  （`torch.stack` 4 列 / 6 列）；
- `scale=1.0` + 默认偏置：`microduck_velocity_env_cfg.py:273` + `use_default_offset=True`
  → `ctrl = default_joint_pos + action`；
- **相位是通过 head/body 指令这两个通道喂进去的**，不是隐藏通道
  → 所以「这类模型输入里没有节拍」那句话**只适用于 velocity/alpha 系列**，不适用于 joy。

### 真正的收获：站桩为什么是他治好的，我们治不好的根本原因

`continuous_joy.patch` 干了三件事：
1. **删掉 8 项奖励**（track_linear/track_angular/air_time/foot_clearance/
   foot_swing_height/head_pose_tracking/head_pose_bias/body_pose_tracking），
   `pose` 1.0→**0.15**，twist 指令全清零。
2. **加时钟化抬脚（权重 12，全场最大）**：
   `target=0.0005+0.024*relu(±sin(2π·1.15t))²`；`reward=exp(-((h-target)/0.009)²).prod(-1)`。
   **std 9 mm、两脚相乘、相位无条件。**
3. 训练量 **600/400/200 iter**（三个 joy 版本），lr 3e-4→2e-4，init_std 0.4。

**关键论证（手算，注意别高估）**：站桩总分 joy ≈7.0/20.2（35%）、我们 7.36/12（61%）
—— **光看总分不够**。决定行为的是：
**踏步时 `joy_balance`/`joy_head`/`pose` 照样能拿满，所以踏步 = 站桩 + 最多 12 分，
没有取舍**；我们的表里"走"要拿 pose/clearance/rate 去换 track，中间一定更差 →
站桩成局部最优。**"严格超集"比"加权和更高"是强得多的性质。**

⚠️ 必须承认的弱点：站桩距目标 2.7σ，**该点梯度只有 ≈4e-4 /mm**。
joy 不是"梯度天然指向踏步"，它靠**值够低 + 探索噪声（init_std 0.4 rad）**。
这正对应 DuckEMW 病历里"air_time 阶跃无梯度"——**它们的解法不是加梯度，
是把站桩那端压到 0，让抖出去一定变好。**

### ① 本仓库自己的解法（一手，最强）：standup 用了**两层高斯**
`microduck_standup_env_cfg.py:295-317` 原文注释：
> Two-layer Gaussian to get both bootstrap reach AND a sharp peak.
> `height_stand` wide std (0.04) for the bootstrap pull; `height_stand_sharp` narrow (0.015)
> for the final cm. **Earlier runs converged at z≈0.109 because the wide-std Gaussian was
> already saturated (0.93/1.0) — no gradient to pull the last cm.**

而 `joy_foot_rhythm` **只有一层、容差 9mm**（`exp(-((z-z_target)/0.009)^2)`）。
→ 当前 actual≈5mm、目标 24mm，误差 19mm = **2.1σ → 奖励 0.0115**；局部斜率
`2·19/81·0.0115 ≈ 0.005/mm`；而在 z=20mm 处是 `2·4/81·0.82 = 0.081/mm`，**差 15 倍**。
→ 即「抬不起来」很可能不是抬不起来，而是**奖励在那个高度上不可见**。

### ② arXiv 2403.05868（humanoid locomotion）：高斯远区梯度趋零 → 用广义 Cauchy 核
原文：Gaussian「gradients may become insignificantly small in distant regions」，而
`C=α((x/σ)^(2β)+1)^-1` 是**重尾**，远处仍有可用梯度，且在 ±σ 处有驻点便于定 σ。→ 备选替换。

### ③ ResGAC training details：σ 是误差容差，且**课程先宽后窄**
「For a tracking kernel exp(−e/σ), the reward falls to 1/e when error equals σ. The width
specifies an error tolerance. The curriculum reduces σ from 0.02 to 0.001 **after the policy
learns to walk**」。→ 若不想改奖励形状，可在 9mm 外面套一个随训练收紧的课程。

### ④ iit-DLSLab basic-locomotion-dls-isaaclab：**每步峰值**跟踪，不要求相位对齐
`feet_height_clearance_periodic = Σ exp(-feet_z_error/0.01) * should_move * ~contact_periodic_on`；
另有 `feet_height_clearance_mujoco_periodic` 维护 `_swing_peak`（落地清零）跟踪**单次腾空最高点**。

`rc_joy.patch` 里 joy cfg 是

这个符号 develop 上没有，上一轮**把三元表达式整个删掉**，理由写成「紧跟的
`if pd_actuators: spec_fn=joy_pd_spec` 已经做了同样的事」。**那句是错的**：
`joy_pd_spec()` 只改 MuJoCo spec 的 `forcerange`，**决定关节由 XML `<position>` 驱动还是由
BAM 电压律驱动的，是 `articulation.actuators`**，它一直是 `FrictionDRBamActuatorCfg`
（kp_fw=200 / vin 6.5–8.2 / delay 3–6 / load-friction DR）。
→ 任务是 `Mjlab-JoySmoothPD`，plant 却是 BAM。**类型是静默的**：任务名、gate、conditioner 全都对。

按 develop 上被注释掉的 `# -- Old actuator (XML position, MuJoCo built-in PD + friction) --`
重建：`pd_actuators = XmlActuatorCfg(target_names_expr=(r"^(?!passive_).*",), delay_min_lag=0, delay_max_lag=3)`
（`delay_*_lag` 按**物理步**计，1 ms/步 → 0–3 ms）。补 `MICRODUCK_STANDUP_PD_ROBOT_CFG`，

### ② 找到自己的一个静默 bug：8hz gate 判据 `or` 与 `max` 不匹配

### 真 bug：`feet_peak` 把两只脚混在一起取中位数
旧：`foot_z.max(dim=0).values.median()`（[T,N,2] → 全部 (env,脚) 一个分布）

| | 值 | gate |
|---|---|---|
| 旧口径 | **20.0 mm** | **PASS** ← 放过一条腿拖地的步态 |
| 新口径（每脚中位数取较差） | **2.0 mm** | FAIL |

而且**危险方向**：拖地的 env 越多，旧口径越容易被抬高的那侧占住中位数。
改法：`peak_per_foot.median(dim=0)` → `min()` 作 gate 值；另报左/右/最差 env。
（第一次负对照用 50/50 构造，`torch.median` 恰好取到低值、两边都 FAIL，**没能区分**——
比例必须按真实情形「多数抬起、少数拖地」构造。）

### 假警报：`min_upright` 的 mean **不该**改
看到 `up.mean(dim=1).min()` 时以为它「先跨 env 平均会抹掉个别摔倒」，改成 per-env median。
**负对照直接推翻**（64 env，upright 0.995→0.10）：

| 摔倒数 | mean（原） | median（我改的） |
|---|---|---|
| 5/64 | 0.925 PASS | 0.995 PASS |
| 10/64 | **0.855 FAIL** | 0.995 PASS |
| 33/64 | 0.534 FAIL | 0.100 FAIL |

mean 下 10/64 摔倒就跌破 0.9，median 要 33/64 —— **我是在「收紧」的名义下把它改松了**。

（注释里第一版写「6/64 就跌破」也是错的，实测 6/64 时 mean=0.911 仍 PASS，已改成 10/64。）

### 教训
**「看起来同类的两个 bug」必须各自构造负对照。** `feet_peak` 是真 bug、`min_upright` 是假警报，
两者代码形状一模一样（都是 `.max(dim=0).median()` / `.mean(dim=1).min()` 这类聚合），
但一个是「混了两个不同物体」，一个是「跨样本平均」——前者错，后者对且更保守。
如果按同一个直觉一起改，就是**一个修好、一个改坏，而且坏的那个会让 gate 变绿**。

## 第四十七轮（15:30–15:55）：三版判据，两版把情况变差，但变差的位置就是答案

### ① 峰值判据（`joy_*_peak`）→ 奖励被饿死

`foot_clearance` / `foot_swing_height` 都以 `command_threshold=0.01`（速度指令）为门控，
joy 把速度指令置零 → 恒不触发 → 上次 `joy_air_time=0`。**思路可留，触发条件要换成相位钟。**
另：官方 `target_height = 0.02` = **20 mm**，与 audit 的 18.46/20.03 一致，我们一直用 24 mm（高 20%）。

### 第六版：窗口峰值 + 线性 20 mm（`patch_joy_peak_linear.py`）
关键实现：**不能 `prod(-1)`** —— 两足交替，乘积永远把摆动足得分乘上站姿足的 0.285。
只评当前摆动的那只脚（`relu(+s)²` 与 `relu(−s)²` 互斥，分母恒 1）。
200 轮结果：`feet_peak` 仍 **0.00533**，但 **8hz 转 PASS（0.00831，rate_rms 1.255→0.965）**，
`joy_feet` 只有 1.30/12。

### 决定性实验：闭环膝偏置探针
`probe_policy_bias_lift.py`：策略正常跑，只给左膝 action 加常值偏置。
```
bias 0.00 → 脚 5.94mm, upright 0.996, 不摔
bias 0.10 → 脚 6.11mm, upright 0.994, 不摔      ← FK 说该涨 2.4mm，实际 0.17mm
bias 0.20 → 脚 38.85mm(摔倒读数), upright 0.350, **摔**
```
**策略在主动抵消抬脚**（0.1 rad 只换 0.17 mm），**且 0.2 rad 就翻**（余量≈0）。
→ 卡点是**局部最优**：「站着不动」是探索唯一能到的零风险策略；24 mm 需要 0.28 rad 多关节
协调，`init_std=0.12` 采不到，任何部分尝试都先翻车。
**这解释了为何五种奖励形状全落在 5.3–5.7 mm：它们要求同一个够不到的台阶，改形状不能让它够到。**

### 第七版：抬脚高度 curriculum（`patch_joy_peak_curriculum.py`，在跑）
target 7→9.5→12.5→16→20 mm，在 0/80/160/240/320 轮切换。起点 7 mm 只比现有 5.94 高一点，
梯度从第 0 步就有且指向可平衡的小幅动作。线性 payoff 保留 → 早期梯度 0.143/mm（σ18 的 3.6 倍）。
`eval` 显式 pin 20 mm，别让验收数字随阶段漂移；日志加 `Metrics/joy_peak_target_m`。

### 探针踩的两个坑
- 开环探针（`probe_openloop_lift.py`）无反馈，全摔（upright 0.42–0.71），数据作废。
  但它「全是垃圾」这件事本身揭示了「抬脚必然破坏平衡」。
- 闭环探针第一版 `site_pos_w[:, :, 2]` 取了全部 7 个 site，列 0 是 `imu`(104mm)，

### 决定性探针 `probe_phase_profile.py`：**单腿踏步，不是「两腿都低」**
按 gait phase 分 24 bin 的脚高（mm）：
```
phase  left   right
0.02  20.09   0.45     左腿在自己摆动窗起点最高
0.52   4.53   4.05
0.98  18.47   0.56
left  mean 9.48 sd 6.54  r(sin)=+0.301
right mean 2.26 sd 1.84  r(sin)=-0.220   ← 负相关：该抬时它压
```

### 顺带修正一个统计口径错误
`Metrics/joy_peak_swing_p50` 取的是**所有 step** 的中位数，而每个摆动窗口只有最后几步才到峰值，
p50 落在爬升段 → 系统性低估。实测 `joy_feet` 6.67/12 → raw 0.556 → 均值等效 11.1mm，
而日志 p50 只有 6.3mm。**两个数不是同一个统计量，都不是 gate 报的那个。**
`probe_peak_spread.py` 改用「窗口末峰值」统计（已写，尚未跑）。

### 第八版方案：只加相位观测，不动奖励（`tools/patch_joy_gait_clock.py`，已写未应用）
相位目前只是**隐式**存在于 head/body 指令里：`head_command=(..., .24 sin p, .12 sin p)`、
`body_command=(..., .006(1-cos 2p), .07 sin p, ...)`。**有 sin 没有可用 cos**
（`1-cos2p` 周期是 p/2，p 与 p+π 不可区分）→ 策略分不清"正在抬"和"正在落"，
而这正是两条腿分工的那半个周期。
→ 加 2 维 `(sin p, cos p)`，用**与奖励同一个** `joy_phase(env)`，保证观测与评分窗口不漂移。
`actor` 输入 +2 → 必须从零重训（AGENTS.md 本来就要求）。部署侧 ONNX 输入宽度同步变化。
**奖励/目标/curriculum 一律不动**，保持单变量：第六版已证明 payoff 能把第一只脚推到 24.5mm。

### 用户第二次问「有没有参考资料」→ 找到逐字命中我们症状的论文
**PhoneBot（arXiv 2610.08737）**：
> "We observed this asymmetric gait, **with the left foot leading and the right foot supporting**,
> on checkpoints trained without mirroring. PhoneBot is left–right symmetric, so that gait is an
> **avoidable bias** rather than a mechanical necessity."

这正是 `probe_phase_profile` 测到的形态。解法与效果：
> sagittal-plane mirror of the collected batch；"After this augmentation is enabled,
> **the walk no longer depends on a single support leg**."（且每步产出 2 个策略样本，tracking reward 提升更快）

镜像定义（IMU 帧 +x 前/+y 左/+z 上）：极向量 `diag(1,−1,1)`；角速度 `diag(−1,1,−1)`；
command `(vx,vy,ωz)`→`diag(1,−1,−1)`；**左右腿交换 + gait-phase 对交换 + 每个 hinge 角取反**；
action 与 Gaussian mean 同样处理、scale 只置换；**value loss 只用真实样本**。

**工具链已内置，无需 hack PPO**（已核实）：
- `rsl_rl/extensions/symmetry.py` 存在；`ppo.py` 支持 `use_data_augmentation` / `use_mirror_loss`
- `data_augmentation_func(env, obs, actions) -> (obs_aug, act_aug)`，shape `[batch*num_aug, ...]`，
  `values/advantages/returns` 由 ppo 自动 `repeat(num_aug)`（与 PhoneBot 的"critic 不估合成轨迹"一致）
- **mjlab 的 agent cfg dataclass 已含 `symmetry_cfg` 字段**（`algorithm` 里，实测 `has symmetry_cfg: True`）
- rsl_rl 文档原话：`use_mirror_loss` "prevents the policy from developing **'limps' or asymmetric
  biases that often occur due to stochastic exploration in symmetric environments**"

**Yu, Turk & Liu 2019（arXiv 1801.08093, "Learning Symmetric and Low-Energy Locomotion"）**：
mirror symmetry loss 必须放 **loss 不放 reward** —— 理由是「把轨迹对称 metric 放进 reward 会 delayed
且 sparse；早期策略产不出结构化周期动作，metric 反而无效」。**再次印证不该继续改 reward。**

### 文献给的三个现成做法

## 战略转折：joy 是 fine-tune 任务，我们从零训 —— 方向反了

用户问「为什么要死磕 joy」并选了「转 swizzle 走路」。执行中发现**两处我自己的错**，
都已撤回，另有一个把整件事重新解释的关键句。

### 错 1：swizzle 不适用腿式（推荐错误，已撤回）

`microduck-社区参考2026-10.md` §8.10 早就记着「swizzle 是 roller 专属的对称"沙漏"步态，
**不适用于腿式**」，我推荐时没查。代码佐证：
- roller（含 swizzle）→ `get_walk_rollers_spec()` → `robot_groundcontact_rollers.xml`
- 腿式走路 → `get_walk_spec()` → **`robot_walk.xml`**
- joy/站立 → `get_standup_spec()` → `robot_groundcontact.xml`

另：官方那句 "does not transfer well to the real robot" 的完整主语是
**`Mjlab-Velocity-Flat-MicroDuck-Rollers`**（轮滑的交替滑步），不是腿式步态。
我之前拿它当「官方承认交替步态难迁移」用，是误读。

### 错 2：`envs 8192 是甜点` 不适用我们（撤回）

那是 `RL_duck` 在 **48 GB** 卡上的吞吐（2048/4096/8192 → 0.033/0.061/0.088 M steps/s）。
`microduck-走起来的配方.md` §6 实测我们在 **8 GB** 卡：8192 比 4096 **慢 4.6 倍**，
**4096 是甜点**（3.08 s/iter，≈31.8k steps/s）。→ `train_joy.sh` 默认 4096 本来就对，不要再推 8192。

### 关键：joy 需要底子，不是从零

`microduck-走起来的配方.md` §5-P-1 里我自己写过一句，直到现在才读懂：
> **Duckverse 自己就是这么走的（先 seed `alpha_walking`，再训 joy，不是反过来）**

Duckverse `run.json`：`resume_index 200 → selected 300`，
`matched_fine_tune_updates_through_selected: 101` —— **他们是 resume 已有 ckpt**。

这解释了全部观察：
| 现象 | 解释 |
|---|---|
| 站得住（Warp 下 min_upright 0.9948） | 从零可以学到平衡 |
| 抬不起脚（6.16mm） | 抬脚是**叠加在已有步态上的调制量**，不是从零能探索出来的 |
| 0757 逐项= Duckverse 配方仍 6.16mm | **缺的是起点，不是配方** |
| Duckverse ONNX 同探针 16.36/17.34mm | 它是 fine-tuned 产物 |

→ **「死磕 joy」的错不在 joy，在顺序。** 最不该做的动作是"再开第十一版从零训"。

### 一个新查出的官方坑（差点让验收读出 0）

`UniformVelocityCommand._update_metrics()` 每步累加 `error / (resampling_time_range[1] / step_dt)`。
所以 **`resampling_time_range` 同时是"重采样间隔"和"metric 的分母"**。
为了固定命令把它设成 `1e9`，分母会变成 5e10 → **`error_vel_xy` 恒为 ~0，看起来完美**。
→ 正解：设成 `(duration, duration)`，分母 = 评测步数，累加值 = 整段平均误差。
   `tools/eval_velocity_in_sim.py:freeze_command` 已按此实现并写明原因。

### 冒烟过程中撞到的两个真 bug（都是"自写"的代价）

- `_step_period` 返回的是**周期（秒）**不是 Hz。当频率用会把 1.15 Hz 读成 0.87 Hz。
- `_step_period` 要 `[T, N]`；传 `lift[:, i, j]`（1-D）→ `IndexError: tuple index out of range`。
  正解 `lift[:, i:i+1, j]`。
- `heading_command=False` 且 `ranges.heading` 非空 → `ValueError: ranges.heading is set but
  heading_command=False`。velocity 原 cfg 是 `heading_command=True` + `rel_heading_envs=0.0`，
  保持 True 才能构建。
