# 平地速度跟踪探索历程（2026-10-24 ~ 10-25）

目标：让 microduck 在**上游默认 flat 任务**（`Mjlab-Velocity-Flat-MicroDuck`）上按指令速度行走，
并且能**证明**它在走（不是微颤、不是滑行、不是原地打转）。

产物：`checkpoints/model_1250.pt`（iter 1250）、`evals/eval_iter1250_clean.json`（11/11 闸门）、
`evals/eval_curve_clean.json`（9 档 checkpoint 同协议曲线）、
`evals/runmeta_vel_4096x12000_1025.json`（训练契约）。方法记录见 `docs/05-flat-walk.md`。

## 0. 先建立参照系（不建参照系，就没有判据）

| 问题 | 答案 | 来源 |
|---|---|---|
| cmd 0.4 下「走多快」算正常？ | 出厂 `alpha_walking.onnx` 只有 **0.164 m/s** | 官方策略库 ONNX + 本仓评估器 |
| 别人 6000 轮练到哪？ | `error_vel_xy` **0.4167**、脚峰 **14.1 mm** | Datawhale 复现（4096×6000，同任务） |
| 0.42 是任务天花板吗？ | **不是** | 同 commit 四拨人卡 0.42–0.43，我们 1250 轮到 0.212 |
| 平地脚该抬多高？ | 上游 `foot_clearance.target_height` = **20 mm** | cfg 原文 |
| 抬得上去吗？ | 关节限位探针：原地抬腿天花板 **25.3 mm** | 本机 Monte Carlo 探针 |
| 66.6 mm 能用吗？ | **不能**——那是官方交替梯策略跨 24–26 mm 级高的 apex | `../simple_stairs/JOURNEY.md` 同一数字的另一用途 |

最后一行是本轮最容易犯的错：把一个**爬楼梯**的脚高当成**平地**的参照，会把 15 mm 的平地脚峰
误判成「完全没抬脚」。

## 1. 时间线

### 2026-10-25 07:00 求解器加固 A/B（**负结果，留档**）

上游 flat 用 `iterations=10 / ls_iterations=20`，加固只写在 `if rough:` 分支。
抬到 100/50 做 A/B：脚峰 2.11/3.25 → 1.82/3.05 mm（冒烟尺度噪声，不是改善），
墙钟 45 → 43 s。⇒ **不是抬脚杠杆**，只当抗 NaN 保险用（长跑 `nan_state` 终止率 0.0000）。

### 2026-10-25 08:10 正式起训（4096 × 12000）

`cfg_sha256_16 = 75a0430b814ac749`、`mdp_sha256_16 = 9f9b77c05d16a1a3`，
`cfg_byte_identical_to_upstream: true` —— **奖励和环境一个字节都没改**。
本地 4070 8 GB，3.14–3.19 s/iter，全程约 10.6 h，¥0。

### 2026-10-25 09:20 iter 1250 首评：先抓到自己的评测 bug

第一次评估判出两条 FAIL：`translates_forward`、`not_sideways`。
「净位移 −0.039 m」看着像原地打转，但同一次运行的**体坐标** ∫vx·dt 是 **+1.6 m**——两个数不可能同时成立。

根因：`reset_base` 的 `pose_range["yaw"] = (-3.14, 3.14)`，各 env 初始朝向全圆周随机，
用世界系 `root_link_pos_w` 求净位移会互相抵消。
修法：投影到各 env **自己的初始朝向**，并把体坐标积分作为独立交叉校验。

修后：`dx_body = +1.575 m`（ratio 0.55）、`|dy_body| = 0.530 m`、10 项闸门全过。
（这两个是**旧协议**读数；同一档 ckpt 在修掉下文 14:00 那个坑后是 `+1.821 m` / `0.476 m`。）
**判据从「结果对不对」改成「两个独立来源是否互相矛盾」**——坐标系/单位/轴的量一律两条算法互校。

### 2026-10-25 09:45 里程碑守候上线

不再靠人盯：`tools/flat_walk/watch_milestones.py` 等 `model_4000.pt` / `model_6000.pt` 落盘，
用**与 1250 完全同参**评测，写 `milestone_verdict.json`；两轮都「无改善」就自动停训（省约 5 h）。
判定阈值写在代码里可审计，并做了 6 例负对照（变好但闸门挂 → flat；速度涨但误差涨 → flat）。

### 2026-10-25 12:03 / 13:59 里程碑判决：**判读规则本身有洞**

守候进程按原规则报 `improved`（4000 误差 −10%、6000 −4%），于是训练继续。
但同一份结果里 vx 从 0.258 掉到 0.209、每脚落地频率从 2.13 掉到 1.40 Hz（均为旧协议读数）——
**「误差降了」和「走得更慢了」是同一件事**。原规则只看 `error_vel_xy`，把这种退化判成了进步。

修法之一：`verdict()` 改成双轴——`error` 变好**且** `vx >= 0.97×` 才算 `improved`，
否则记为 `trade`（`docs/05-flat-walk.md` §2b 的曲线就是这么来的）。

### 2026-10-25 14:00 追下去发现更糟：25% 的 env 被静默改成「站着别动」

`error_vel_xy` 的算术下界是 `|cmd - mean(vx)|`。4000 档实测 0.174，而 `|0.4 − 0.167| = 0.233`
——**读数低于自己的下界，说明分母里有东西不是我以为的那个**。

逐层查下去：`_update_metrics` 是 `||cmd − v||` 的均值，公式没错；错的是 `cmd`。
`freeze_command()` 确实把 `rel_standing_envs` 设成 0，但 cfg 里还有个 `standing_envs`
课程项，**每一步**按 `common_step_counter` 重写这个字段（`mdp.py:3440-3474`，末级 0.25），
而让评测可复现的做法正是把计数器钉到 1e9。于是每次评测都有 25% 的 env 在「站着」，
它们的误差≈0，把均值稀释；而 25% 是按 env 独立抽取的，**每次抽到的个数不同（32 个里 6–10 个）**，
稀释比例就随机游走，两次评测的差值被读成了「进步」。

修后重测（32 env 全走，新增 `command_frozen_ok` 协议闸门）：

| | 旧协议 | 修后 |
|---|---|---|
| 1250 `error_vel_xy` / vx | 0.194 / 0.258 | **0.212 / 0.252** |
| 4000 `error_vel_xy` / vx | 0.174 / 0.209 | **0.234 / 0.220** |
| 4000 相对 1250 | 好 10% | **差 10%** |

**符号反了。** 补上负对照：把 `pop` 那行去掉重跑，`command_frozen_ok` 立刻 FAIL 并打印
`uniq vx [0.0, 0.4] / frac cmd==0 25.0%`。

### 2026-10-25 14:20 扫描 9 档 checkpoint，确认 1250 是峰值

既然 4000/6000 变差，就把每 250 轮存档全测一遍（每档 ~55 s）：
1250 最好，1750–2000 塌陷（跟踪与误差双 FAIL），2500–4000 部分回升但**一次都没回到 1250**，
6000 再跌一个 `no_fall`。`mean_action_acc` 却从 0.0747 单调降到 0.0604——越来越平滑、越来越慢。
⇒ **在 6000 停训**（原计划 12000，省 5.3 h），ckpt 全留、续训脚本在，决定可逆。

## 2. 判决

**1250 即峰值，配方不动。** 9 档曲线证明后 4750 轮都在把「跟踪」换成「平滑」，
不是欠训练；`error_vel_xy 0.212`、11/11 闸门，已经超过公开的 5000–6000 轮水平。
若目标是「真的按 0.4 走」（当前 63%），瓶颈不在轮数而在奖励形状——那才是 issue #46 那个
补丁的用途，而不是现在这个已经过闸的策略。

**issue #46 三处改法**仍写成了可回滚补丁 `tools/flat_walk/patch_issue46.py`
（`--check/--apply/--revert`，幂等、带备份、复用上游 `_forward_progress_gate`），
但**当前刻意保持 `NOT applied`**，只作为换任务时的待用件。

### 2.1 验收：分层看，别把「闸门全过」读成「达到预期」

收尾时被问了一个好问题——「效果达到预期了吗」。按层拆开，答案不一样（详见 `docs/05-flat-walk.md` §9）：

| 层 | 结果 |
|---|---|
| 工程闭环（从零训练 / ¥0 / 可复现 / 证据入库） | 达标 |
| 会走（速度 + 抬脚 + 交替 + 不摔） | 达标 |
| 跟得准（cmd 0.4） | **未达标**，63% |
| 走直线（保持航向） | **任务本身没要求**——`rel_heading_envs = 0.0` |

两条容易读错的：① 闸门阈值 `error_vel_xy ≤ 0.25` 是按**及格**设的，11/11 不等于优秀；
② 侧视片里「鸭子走到一半转向镜头」不是打转，`wz` 带符号平均只有 1.8 °/s，
绝对值平均却有 17 °/s ⇒ 它在**左右晃**。要修就收紧 `track_angular_velocity`（现在
`std=sqrt(0.5)` 让 wz 偏 0.3 时奖励还有 0.914），而不是加一个锁死世界朝向的 heading 惩罚。

## 3. 留给下一个人的三句话

1. **先测参照，再看结果**：没有出厂 0.164 / Datawhale 0.4167 这两个数，你无法判断 0.25 是好是坏。
2. **任何坐标系转换，必须两条独立算法互校**；静默 bug 的输出总是落在「看起来合理」的区间里。
3. **上游 cfg 的字节哈希要进 runmeta**：`cfg_byte_identical_to_upstream: true` 是「我没偷偷改奖励」
   唯一的机器可验证证据。
4. **「我设了这个字段」不等于「这个字段还是这个值」**：只要还有第二个写者（课程、manager、reset
   事件），冻结就必须**可测量**（记录每步的 `cmd` 并当闸门），不能是声明式的。这次的代价是
   一个反了符号的结论 + 差点为「变慢」再付 5 小时 GPU。
